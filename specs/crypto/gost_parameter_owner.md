# GOST parameter and verification ownership

The five admitted GOST algorithm identities obtain their curve integers from `crates/iroha_crypto/src/signature/gost/parameters.rs`. Signing constructs its outer integer representation and fixed-width point operations from these literals. Verification uses the same literals throughout its fixed-width field, scalar and point relation. Public keys encode little-endian `x || y`; signatures encode little-endian `r || s`, each coordinate/scalar using its parameter set's full 32-byte or 64-byte width.

The 256-bit A/B/C coordinates are the CryptoPro A/B/C sets in [RFC 4357 section 11.4](https://www.rfc-editor.org/rfc/rfc4357#section-11.4). The 512-bit A/B sets are specified in [RFC 7836 appendix A.1](https://www.rfc-editor.org/rfc/rfc7836#appendix-A.1). The Iroha algorithm identities designate exactly those sets. There are no alternate parameter decoders or aliases.

`gost/constant_time/verification.rs` owns the single verification relation. It checks exact widths before fixed-integer conversion, canonical coordinates below `p`, the curve equation, and nonzero `r,s < q`. Streebog-256 or Streebog-512 digest bytes use the same big-endian scalar interpretation as signing, reduced modulo `q`, with zero replaced by one. The relation computes `e^-1`, `z1=s/e`, `z2=-r/e`, and `z1 G + z2 Q`; infinity is rejected before comparing its affine x coordinate modulo `q` with `r`.

Ordinary, typed, admission, and explicit owned-key verification use this relation. Compact public keys borrow their canonical bytes during validation and verification; GOST has no decoded-key cache producer or retained decoded-key variant. The explicit owned `gost::PublicKey` facade retains one payload allocation and delegates to the same relation. Signing and private-key generation retain their existing allocation obligations.

Successful borrowed key validation and verification use inline fixed-width storage. The decode success descriptor therefore charges no parser heap units; it still funds the compact key's exact retained allocation separately. Fixed internal rejection descriptors materialize existing public `ParseError(String)` diagnostics only at the facade boundary. **TODO: fund public malformed-key diagnostics and the subsequent Norito `Message(String)` conversion before allocation.** The zero-success descriptor does not claim that error paths, owned public-key construction, private-key operations, or all Crypto resources are funded. Inline scratch still requires inclusion in execution stack admission.

The old fixed backend duplicated the subgroup order for 256-A and 512-A with an incorrect `fe` byte where the canonical production value has `ff`. Its production point operations did not use that duplicated scalar-order field: scalar validation, inversion and reduction used the outer canonical order. The shared literal owner removes that mismatch before fixed scalar verification uses the order. All six canonical outer integers and all five diagnostic names are preserved; no fixture pins are regenerated.

Controls cover all six curve integers and widths, independent affine `qG`/`(q-1)G`, full-width field/scalar boundaries, digest reduction and inversion, joint-relation infinity, key/signature/message mutations, borrowed-key identity, cache exclusion, malformed-key error ordering, and the actual global allocator on ordinary/typed/admission/owned facades. The repository's `wycheproof_gost.json` contains locally generated deterministic vectors; its filename does not establish independent upstream vector provenance. Hardware parity, strict linting and candidate qualification require their own exact-candidate receipts. Source extraction or matching an independent arithmetic control is not a release qualification claim.
