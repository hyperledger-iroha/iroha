# Configuration Overview

This page summarizes the top-level sections of the Iroha configuration file (TOML) and what each controls. For a concrete template, see `specs/references/peer.template.toml`.

Defaults first: configuration values are curated for typical Iroha blockchain deployments. In most cases, you can run with the defaults unchanged. Only adjust settings when you have a specific operational need (e.g., custom ports, strict rate limits, or known network constraints).

- Sora-specific sections (`sorafs.*`, multi-lane `nexus.*`) require starting the daemon with `irohad --sora …` (or exporting `IROHA_SORA_PROFILE=1`). Without the flag the loader rejects configurations that enable those features.
- When `nexus.enabled = false` (Iroha 2 mode), configs stay single-lane: `/status` and `/v1/sumeragi/status` hide lane/dataspace sections, `/metrics` skips lane/dataspace labels entirely, and lane-scoped status tails return `StatusSegmentNotFound` so SDKs must branch on the flag before sending lane parameters. Config parsing rejects lane/dataspace/routing overrides in this mode—strip `nexus.*` sections unless you enable Nexus/Sora with `nexus.enabled=true` or `--sora`.
- `[common]`: Chain identity (`chain`), node key pair, trusted peers, the default domain label used only when encoding/compressing `AccountAddress` selectors (`default_account_domain_label`), and the i105 chain discriminant (`chain_discriminant`). `chain` is exact, case-sensitive ASCII of 1–128 bytes; it starts and ends with an alphanumeric and otherwise permits only alphanumerics plus `.`, `_`, `:`, and `-`. Assign a unique value to every distinct deployment/replay domain. `AccountId` literals themselves are canonical domainless i105 and do not infer scope from this setting.
- Identity separation: the `public_key`/`private_key` pair is the node's transport + consensus identity and must be BLS‑Normal for validator nodes; validator identities must appear in `trusted_peers` alongside a valid PoP in `trusted_peers_pop`. Trusted peers without PoPs are network-trusted observers and are excluded from consensus. Config parsing rejects invalid PoPs or PoP maps that reference keys outside `trusted_peers`. `crypto.allowed_signing`/`allowed_curve_ids` gate transaction admission and non-consensus account controllers; BLS validator accounts are accepted even if `allowed_signing` omits BLS. Add `bls_normal` to `allowed_signing` only when you intend to accept BLS‑signed transactions.
- `[genesis]`: Location of the signed genesis file and the public key used to verify it. The referenced manifest carries parameter families such as `transaction.max_signatures`, `transaction.max_instructions`, `transaction.ivm_bytecode_size`, `transaction.max_tx_bytes`, `transaction.max_decompressed_bytes`, and `transaction.max_time_to_live_ms`; update the manifest when tightening admission limits. `max_time_to_live_ms` defaults to one day and is the on-chain ceiling for every signature-bound transaction TTL. Nodes that start with empty storage and no local `genesis.file` may fetch genesis from trusted peers only when `bootstrap_enabled = true` and `expected_hash` pins the exact signed genesis consensus-header hash. That header commits the ordered transaction intents through their Merkle root; genesis admission recomputes the root and verifies the single genesis-authority block signature. Enabling the remote path without the pin is a startup configuration error before any request is sent. A local signed `genesis.file` is already an explicit artifact and needs no additional hash pin. Operators may supply a `bootstrap_allowlist` (defaults to `trusted_peers`) and bound the transfer via `bootstrap_max_bytes` and `bootstrap_response_throttle_ms`. Bootstrap honours `bootstrap_request_timeout_ms` and `bootstrap_retry_interval_ms`; `bootstrap_max_attempts` is the number of unanswered windows in one diagnostic/backoff cycle, after which backoff resets and enabled bootstrap continues rather than failing permanently during a partition. Responders always enforce chain-id/public-key/hash matches and reject oversized payloads or non-allowlisted peers.
- `[network]`: P2P addresses, gossip periods/sizes, DNS refresh, bounded queue capacities, and transport options (TLS/QUIC plus automatic SCION preference when both peers advertise support). Deferred outbound sends are bounded by age, per-peer count/stream-wire bytes, and the true-total `network.deferred_send_max_bytes_total` cap (128 MiB by default). The total owner keeps an additive authenticated-consensus safety reserve; ordinary traffic cannot consume it.
- Consensus ingress guardrails: `network.consensus_ingress_rate_per_sec`/`consensus_ingress_burst` cap per-peer consensus/control frames (`null` disables), `network.consensus_ingress_bytes_per_sec`/`network.consensus_ingress_bytes_burst` cap payload volume, `network.consensus_ingress_critical_rate_per_sec`/`consensus_ingress_critical_burst` and `network.consensus_ingress_critical_bytes_per_sec`/`network.consensus_ingress_critical_bytes_burst` apply dedicated caps to liveness-critical messages (fallback to the standard caps when both critical caps are unset; penalty cooldowns apply in that fallback), `network.consensus_ingress_rbc_session_limit` bounds concurrent RBC sessions per peer (auto-raised to at least `2 * (rbc_session_ttl / block_time)`; set `0` to disable), and `network.consensus_ingress_penalty_threshold` + `network.consensus_ingress_penalty_window_ms` + `network.consensus_ingress_penalty_cooldown_ms` temporarily suppress peers that exceed the standard caps. Critical recovery/coordination and payload delivery (`BlockCreated`, `FetchPendingBlock`, `ProposalHint`, `Proposal`, `QcVote`, `Qc`, `VrfCommit`, `VrfReveal`, `RbcInit`, `RbcReady`, `RbcDeliver`, plus control-flow evidence) uses the critical caps and skips penalty cooldowns unless critical caps are disabled; bulk payload frames (`BlockSyncUpdate`, `ExecWitness`, `RbcChunk`, and `BlockSync` requests/responses) use a separate bulk bucket seeded from the standard caps, scaled against the 2s default block time (1s -> 2x), and skip penalty cooldowns while still tracking RBC session limits.
- `[ivm]`: Runtime VM settings. `ivm.memory_budget_profile` (default: `compute.default_resource_profile`) selects which compute resource profile supplies `max_stack_bytes` as the guest stack budget cap.
- `[pipeline]`: Transaction pipeline parallelism and caches. `pipeline.workers` (0 = auto) sets the worker pool used for the stateless pre-pass, access derivation, and overlay construction; `pipeline.stateless_cache_cap` bounds the stateless validation cache (0 disables it) so identical transactions can skip repeat pre-pass checks until TTL/clock-drift windows expire.
- `[tiered_state]`: Hot/cold WSV tiering knobs (`enabled`, `hot_retained_keys`, `hot_retained_bytes`, `hot_retained_grace_snapshots`, `cold_store_root`, `da_store_root`, `max_snapshots`, `max_cold_bytes`). If `cold_store_root` is unset, snapshots are stored under `da_store_root`; changing either root resets tiering metadata.
- `[concurrency]`: Thread-pool sizing plus stack budgets for Tokio runtime/blocking threads, scheduler/prover workers, and the IVM guest. `tokio_stack_bytes` defaults to 8 MiB and is validated within 8–64 MiB so Torii and embedded production services have a consistent startup envelope instead of inheriting the platform thread default. `gas_to_stack_multiplier` (default `4`) bounds guest stack space as `min(guest_stack_bytes, gas_limit * multiplier, stack_budget)` with a 64 KiB floor and 1 GiB ceiling; `stack_budget` comes from the `ivm.memory_budget_profile` selection. Requests outside that window are clamped, logged, and exported via `/status.stack` and the `iroha_ivm_stack_*` metrics (including pool-fallback/budget-hit counters). Lower the multiplier to cap recursion on low-gas routes or raise it (within the guest stack cap) to admit deeper Kotodama frames.
- `network.peer_gossip_period_ms` (default: `1000`ms) also governs the topology refresh cadence. The `IROHA_P2P_TOPOLOGY_UPDATE_MS` env override is now ignored; adjust the config field instead. Peer-address gossip backs off when idle up to `network.peer_gossip_max_period_ms`, and block-sync sampling backs off up to `network.block_gossip_max_period_ms`. Gossip periods (`block_gossip_period_ms`, `block_gossip_max_period_ms`, `transaction_gossip_period_ms`, `peer_gossip_period_ms`, `peer_gossip_max_period_ms`), `idle_timeout_ms`, and `reply_writer_flush_timeout_ms` are clamped to a minimum of 100ms to avoid tight loops. `reply_writer_flush_timeout_ms` defaults to 30 seconds and is the base deadline for one exact reply's peer-writer occurrence; only an observed timeout increases that item's next deadline, while a successful full flush resets it.
- SCION transport selection is capability-driven and automatic: peers advertise `scion_supported` in handshake/trust metadata and peer gossip, and outbound dialing prefers SCION-capable paths only when both sides advertise support. Legacy non-SCION peers continue to use the existing QUIC/TLS/TCP fallback path automatically. Existing `network.scion_*` fields are ignored and retained only for backward-compatible config parsing.
- `network.trust_gossip` (default: `true`) advertises support for TrustGossip frames. Setting it to `false` negotiates the capability off at handshake time, dropping TrustGossip messages while leaving peer-address gossip intact. Drops are tagged via `p2p_trust_gossip_skipped_total{direction,reason}` so operators can spot opt-outs or peers that refused the capability.
- Trust scoring knobs under `[network]` (`trust_decay_half_life_ms`, `trust_penalty_bad_gossip`, `trust_penalty_unknown_peer`, `trust_min_score`) apply in permissioned overlays: trust frames that reference peers outside the active topology incur the unknown-peer penalty, increment `p2p_trust_penalties_total{reason="unknown_peer"}`, and senders below `trust_min_score` are ignored until decay recovers. Public/NPoS overlays skip the unknown-peer penalty so trust gossip remains open.
- Transaction gossip tuning: `network.transaction_gossip_drop_unknown_dataspace` drops batches for dataspaces missing from the lane catalog; `network.transaction_gossip_restricted_target_cap` caps restricted fanout (defaults to the full commit topology); `network.transaction_gossip_public_target_cap` caps public-lane fanout (default 16, set `null` for broadcast); `network.transaction_gossip_public_target_reshuffle_ms` and `network.transaction_gossip_restricted_target_reshuffle_ms` control how often target selection reshuffles per plane (defaults to `transaction_gossip_period_ms`, clamped to ≥100ms); `network.transaction_gossip_resend_ticks` sets how many gossip periods elapse before re-sending the same transactions (higher reduces duplicate traffic); `network.transaction_gossip_restricted_fallback` (`drop` | `public_overlay`) controls whether restricted gossip falls back to online peers when the commit topology is empty; and `network.transaction_gossip_restricted_public_payload` (`refuse` | `forward`, default `refuse`) currently refuses to leak restricted payloads when only the public overlay is available (forwarding is blocked until encrypted transport lands). Telemetry surfaces the drop/forward policy via gauges and `/status.tx_gossip` entries (caps, targets/peers, fallback surface, reason/outcome) so operators can alert on blocked or rerouted batches.
- `network.soranet_handshake.pow`: Challenge configuration for SoraNet admission. Fields: `required`, `difficulty`, `max_future_skew_secs`, `min_ticket_ttl_secs`, `ticket_ttl_secs`, `revocation_store_capacity`, `revocation_max_ttl_secs`, and `revocation_store_path`. The revocation store controls how many signed tickets are retained on disk and how long they remain valid for replay detection.
- `network.soranet_handshake.pow.puzzle`: mandatory Argon2 puzzle settings. The first-release resource corridor is `memory_kib = 4096..=131072`, `time_cost = 1..=8`, `lanes = 1..=16`, and `difficulty = 0..=32`; runtime updates outside those bounds are rejected atomically. Handshake security policy is node-local operator configuration and is never accepted from or propagated through P2P messages.
- `network.soranet_handshake.kem_suite`: Optional textual override (`"mlkem512"`, `"mlkem768"`, or `"mlkem1024"`; `kyber*` aliases are also accepted) for the ML-KEM profile used during the SoraNet handshake. When set it supersedes `kem_id` and validates the configured Kyber key lengths for the selected suite.
- `[sumeragi]`: Consensus role (validator/observer) and collector settings (K, redundant-send r, parallel topology fanout), plus timing slack options. When `sumeragi.da.enabled=true`, availability evidence (availability votes or an RBC `READY` quorum) is tracked (advisory; does not gate commit/finalize); missing local payloads are fetched via RBC or block sync and can defer quorum rescheduling. Availability deadlines are scaled by `sumeragi.advanced.da.quorum_timeout_multiplier` and `sumeragi.advanced.da.availability_timeout_multiplier`, with `sumeragi.advanced.da.availability_timeout_floor_ms` enforcing a minimum window for logging/rebroadcast heuristics. Per-queue backpressure is configured with `sumeragi.advanced.queues.votes`, `sumeragi.advanced.queues.block_payload`, `sumeragi.advanced.queues.rbc_chunks`, `sumeragi.advanced.queues.blocks`, and `sumeragi.advanced.queues.control`; legacy `msg_channel_cap` acts as a fallback only when per-queue caps are omitted, and proposal assembly defers while the block-payload/RBC-chunk queues are saturated. Pacemaker deferrals also gate on pending blocks after `sumeragi.advanced.pacemaker.pending_stall_grace_ms` of no progress (set 0 for immediate gating) and unresolved RBC backlog; set `sumeragi.advanced.pacemaker.active_pending_soft_limit`, `sumeragi.advanced.pacemaker.rbc_backlog_session_soft_limit`, and `sumeragi.advanced.pacemaker.rbc_backlog_chunk_soft_limit` to allow a small backlog before deferral (0 keeps strict gating). Deterministic pacing governor (`sumeragi.advanced.pacing_governor`) is always enabled and adjusts `pacing_factor_bps` at block boundaries based on view-change pressure and commit spacing with bounded hysteresis. Experimental vNext performance-fault knobs live under `sumeragi.advanced.vnext`: `performance_window_samples`, `suspicion_timeout_ms`, `performance_threshold_bps`, `max_tainted_per_view`, and `rechain_cooldown_ms`; the legacy loop only parses these until the vNext reactor is wired into runtime. The worker loop time budget is capped by `sumeragi.advanced.worker.iteration_budget_cap_ms` (clamped to 2000ms max); mailbox draining per iteration is further capped by `sumeragi.advanced.worker.iteration_drain_budget_cap_ms` to keep ticks on schedule under backlog. Per-tick proposal/commit work can be capped with `sumeragi.advanced.worker.tick_work_budget_cap_ms` (default 500ms; 0 disables); tick cadence floors to this cap so ticks cannot schedule faster than the budget. Parallel ingress processing for consensus queues is controlled by `sumeragi.advanced.worker.parallel_ingress` (default `true`). Pre-vote validation offload scales with `sumeragi.advanced.worker.validation_worker_threads` (0 = auto → available cores) plus `sumeragi.advanced.worker.validation_work_queue_cap`/`sumeragi.advanced.worker.validation_result_queue_cap` (0 = auto → derived from worker count), with `sumeragi.advanced.worker.validation_pending_cap` bounding the deferred vote-validation backlog; QC aggregate verification uses `sumeragi.advanced.worker.qc_verify_worker_threads` plus `sumeragi.advanced.worker.qc_verify_work_queue_cap`/`sumeragi.advanced.worker.qc_verify_result_queue_cap` (0 = auto → derived from worker count). `sumeragi.advanced.rbc.chunk_fanout` caps per-chunk RBC broadcasts (`null` = full roster minus local) and `sumeragi.advanced.rbc.payload_chunks_per_tick` limits how many RBC chunks broadcast per tick to avoid bursty floods. Block payloads always respect `sumeragi.block.max_payload_bytes` plus the consensus payload frame cap; in DA mode the effective payload budget is the minimum of that cap, the RBC chunk budget, and `sumeragi.advanced.rbc.pending_max_bytes`/`sumeragi.advanced.rbc.pending_max_chunks` so INIT‑less chunk stashes fit within bounds and `BlockCreated`/`BlockSyncUpdate` frames remain sendable. Pending RBC stashes are capped across sessions by `sumeragi.advanced.rbc.pending_session_limit`. `sumeragi.mode_flip.enabled` (default `true`) acts as an operator kill switch for live permissioned↔NPoS cutovers: when `false` the node advertises the staged mode via status/telemetry but refuses to flip until the flag is restored. Persistence failures back off according to `sumeragi.persistence.kura_retry_interval_ms`/`sumeragi.persistence.kura_retry_max_attempts` so blocks stay pending until Kura accepts them or the retry budget is exhausted; `sumeragi.persistence.commit_inflight_timeout_ms` aborts stuck commit jobs so proposals cannot stall indefinitely, and `sumeragi.persistence.commit_work_queue_cap`/`sumeragi.persistence.commit_result_queue_cap` bound commit worker queues. Missing-block fetch prefers certificate signers for `sumeragi.recovery.missing_block_signer_fallback_attempts` attempts (default 1; set 0 to skip signer preference) before falling back to the full commit topology. Recovery tuning also exposes `sumeragi.recovery.deferred_qc_ttl_ms`, `sumeragi.recovery.missing_block_height_attempt_cap`, `sumeragi.recovery.missing_block_height_ttl_ms`, `sumeragi.recovery.sidecar_mismatch_retry_cap`, `sumeragi.recovery.sidecar_mismatch_ttl_ms`, and `sumeragi.recovery.range_pull_escalation_after_hash_misses` plus backlog-aware view-change grace controls (`sumeragi.recovery.view_change_backlog_extension_factor`, `sumeragi.recovery.view_change_backlog_extension_cap_ms`), which only apply when RBC/consensus backlog signals are active. Membership hash drift is surfaced through `sumeragi.gating.membership_mismatch_alert_threshold` (consecutive mismatches before alerting) and `sumeragi.gating.membership_mismatch_fail_closed` (drop consensus messages from still-mismatching peers). Future gating drops consensus messages beyond `sumeragi.gating.future_height_window`/`sumeragi.gating.future_view_window` (set either to `0` to disable that dimension). View gating only applies to the active round and relaxes after the local commit-quorum timeout so lagging nodes can catch up; block-sync updates respect the same windows unless the payload is already tracked (pending or explicitly requested) or the parent payload is already known, so catch-up sync stays bounded. Invalid-signature suppression uses `sumeragi.gating.invalid_sig_penalty_threshold`, `sumeragi.gating.invalid_sig_penalty_window_ms`, and `sumeragi.gating.invalid_sig_penalty_cooldown_ms` to temporarily ignore signers that keep emitting bad signatures. The pacemaker proposal interval is derived from on-chain `SumeragiParameters.block_time_ms (scaled by pacing_factor_bps)`, `sumeragi.advanced.npos.timeouts.propose_ms`, `sumeragi.advanced.pacemaker.rtt_floor_multiplier`, and capped by `sumeragi.advanced.pacemaker.max_backoff_ms`; raise the RTT floor or block time to slow proposals on high-latency links. Unset `sumeragi.advanced.npos.timeouts.*_ms` and `sumeragi.npos.vrf.*` fields derive from `SumeragiParameters.block_time_ms (scaled by pacing_factor_bps)` and `sumeragi.npos.epoch_length_blocks` using the default ratios. RBC READY/DELIVER quorum always follows the commit topology (`Topology::min_votes_for_commit()`).
- `[torii]`: Public API server settings such as listen address, request size caps, and query store parameters.
- `[torii.transaction_ingress]`: Physical transaction-submission resource corridor.
  `max_concurrent_compute_jobs` (default: `4`) bounds blocking transaction
  admission work: batch-envelope and transaction decode, canonicalization,
  signature verification, routing, and atomic queue admission across single,
  entrypoint, and batch submission routes. Torii fails fast when all slots are
  occupied, and each owned slot remains in the physical worker until it exits
  even if the HTTP request times out or disconnects.
  `max_batch_transactions` (default: `512`) is the exact top-level transaction
  count accepted by `/v1/pipeline/transactions/batch`. Torii authenticates and
  enforces encoded and declared-decoded byte limits before compute admission,
  then uses Norito's authoritative sequence decoder to reject count overflow
  and exact queue pressure before decoding any signed transaction payload.
- `torii.receipt_public_key` / `torii.receipt_private_key` (optional): Key pair used to sign transaction submission receipts. If omitted, `irohad` generates an ephemeral Secp256k1 signer at startup; set both values to keep receipts stable across restarts. BLS keys are rejected here—use Ed25519 or Secp256k1.
- `[torii.operator_auth]`: WebAuthn/mTLS gate for operator endpoints. `enabled` turns on operator authentication; `require_mtls` enforces ingress mTLS (expects `X-Forwarded-Client-Cert` from the edge proxy). `token_fallback` controls bootstrap token usage (`disabled|bootstrap|always`), `token_source` selects `operator|api|both`, and `tokens` configures the operator-token allowlist. `rate_per_minute`/`burst` apply to auth attempts, while `lockout.{failures,window_secs,duration_secs}` controls temporary lockouts. `webauthn` is required when `enabled = true` and configures `rp_id`, `rp_name`, `origins`, `user_id`, `user_name`, `user_display_name`, `challenge_ttl_secs`, `session_ttl_secs`, `require_user_verification`, and `allowed_algorithms`. Credentials persist under `<torii.data_dir>/operator_auth/operator_webauthn.json`. When `token_fallback = "bootstrap"`, tokens are accepted only until the first credential is enrolled; after that operators must log in and send `x-iroha-operator-session`.
- `torii.events_buffer_capacity` (default: `10000`): Broadcast channel size used for `/v1/events/sse` and webhook enqueuing. Lower the value to bound memory/backpressure when subscribers lag.
- `torii.ws_message_timeout_ms` (default: `10000`): WebSocket message timeout (read/write) for Torii event/block streams; increase it for slow clients or high-latency links.
- `torii.app_api.*`: Pagination/backpressure defaults for JSON convenience endpoints. `default_list_limit` seeds `limit` when omitted, `max_list_limit` and `max_fetch_size` bound page/fetch sizes, and `rate_limit_cost_per_row` controls how much each requested row costs under the app API rate limiter.
- `[torii.recipient_lookup]`: Privacy-minimized retail routing and bank-name lookup. `policy_id` (default `cbuae_aed_sbp_pkr`) selects the governed FX corridor policy and `requests_per_minute` (default and maximum `30`) applies a dedicated per-signer limiter shared by `POST /v1/retail/recipients/route` and `POST /v1/retail/recipients/lookup`. Both endpoints require canonical request signing, an existing signer, an enabled policy whose source is `transaction_authority`, and a positive signer balance in that policy's source asset/dataspace. `request_timeout_ms` bounds configured upstream bank calls and each `[[torii.recipient_lookup.routes]]` entry supplies an exact `fi_id` (`hbl.sbp` or `ubl.sbp`), `base_url`, and private `bearer_token`. `/route` returns only `{account_id, alias_fqn, fi_id}`; `/lookup` additionally contacts the selected bank route. Fee sponsorship is separate: account-signed `POST /v1/fee-sponsor-programs/by-id` reads one exact lifecycle record, while account-signed `POST /v1/fees/quote` evaluates the exact unsigned transaction payload through the canonical admission router. Neither endpoint synthesizes a fallback program or payer.
- `torii.webhook.*`: Delivery/backoff tuning for the webhook worker. `queue_capacity` caps on-disk pending deliveries (default: `10000`), `max_attempts` bounds retries (default: `12`), `backoff_initial_ms`/`backoff_max_ms` set the exponential retry window (defaults: `1000`/`60000`), and `{connect,write,read}_timeout_ms` configure HTTP timeouts for delivery attempts.
- `torii.push.*`: Best-effort account activity push delivery. `enabled` starts a Torii-only worker that watches committed blocks, stores device registrations under `<torii.data_dir>/push/`, queues minimal account-activity payloads, and retries provider delivery without affecting consensus. `rate_per_minute`/`burst` limit device registration, `max_topics_per_device` bounds stored topic labels, and `connect_timeout_ms`/`request_timeout_ms` bound FCM/APNs HTTP attempts. FCM HTTP v1 requires `fcm_project_id` plus `fcm_service_account_path`; the legacy `fcm_api_key` field is parsed for compatibility but not used for delivery. APNs token auth requires `apns_environment` (`sandbox` or `production`), `apns_topic`, `apns_team_id`, `apns_key_id`, and `apns_private_key_path`; `apns_endpoint` is only an override for tests or private deployments, and `apns_auth_token` is deprecated.
- `torii.da_ingest.*`: Replay cache and manifest spool configuration for the DA pipeline.
  - `max_concurrent_compute_jobs` (default: `1`) bounds physical signature verification,
    normalization, chunking, RS16, manifest, and PDP work. These phases run through
    `spawn_blocking` only after acquiring an owned semaphore permit; the worker retains that
    permit through physical completion even if the originating HTTP request is cancelled.
  - `replay_cache_capacity` (default: `4096`) bounds cached sequence fingerprints inside each
    `(lane, epoch)` window. `replay_cache_max_lane_epochs` (default: `1024`) is the independent
    global bound on distinct windows across memory, durable cursor recovery, and telemetry labels.
    Admission fails closed when that global capacity is full; startup also fails closed if a
    checkpoint or journal exceeds it.
  - `replay_cache_store_dir` (default: `./storage/da_replay`) contains a bounded append journal and
    its canonical checkpoint. Cursor advances append and sync one checksummed record; after at most
    `replay_cache_max_lane_epochs` records Torii checkpoints the bounded map and truncates the
    journal. A torn final frame is truncated during recovery, while a corrupt complete frame,
    symlink, or conflicting checkpoint aborts startup rather than silently discarding replay state.
  - `replay_cache_ttl_secs` (default: `900`) controls in-memory fingerprint retention and
    `replay_cache_max_sequence_lag` (default: `4096`) rejects old sequences behind a window's
    high-water mark. Durable high-water marks remain authoritative across restarts.
  - `telemetry_cluster_label` (optional): Sets the `cluster` label emitted on Taikai ingest/viewer metrics so dashboards can distinguish environments (e.g., `region-a` vs `staging`).
    Set `governance_metadata_key_hex` to a 32-byte ChaCha20-Poly1305 key when you need
    Torii to seal governance-only metadata; pair it with `governance_metadata_key_label`
    (a short identifier such as `"primary"`) so encrypted entries advertise which key
    produced the ciphertext. Torii encrypts cleartext governance metadata automatically
    and refuses manifests whose pre-encrypted payloads carry missing or mismatched labels.
    The nested `replication_policy` table defines the enforced `RetentionPolicy` per
    blob class (see `specs/da/replication_policy.md`). Override `default_retention`
    to change the baseline hot/cold windows and add entries under
    `replication_policy.overrides` (e.g., `class = "taikai_segment"`) to tighten
    specific classes; Torii rewrites caller-supplied manifests to match these values
    and rejects mismatched envelopes.
  - `debug_match_filters` (default: `false`) enables deterministic filter-debug traces formerly gated by the `TORII_DEBUG_MATCH` environment toggle. Keep this off in production.
- `[torii.iso_bridge.reference_data]`: Paths to ISO reference datasets (`isin_crosswalk_path`, `bic_lei_path`, `mic_directory_path`), the ingest cadence (`refresh_interval_secs`), and optional `cache_dir` for persisting copies plus provenance metadata (version/source/checksum) of each loaded snapshot.
- `[torii.iso_bridge.profiles]`: Operator ISO 20022 rail profile overrides. For `require-verified` XMLDSig/XAdES profiles, configure `signature_public_key_sha256_pins` for raw XMLDSig keys and `x509_trust_anchor_sha256_pins` for linked terminal CA DER certificate pins in verified X.509 chains. Stale `trusted_public_key_sha256` and `trusted_certificate_sha256` aliases are rejected. SHA-256 pin strings must already be canonical lowercase 64-character hex values. Rotate certificate anchors by first trusting both the current and next anchor digests, then removing the retired digest after the upstream cutover is complete. If an anchor or leaf is compromised, add its DER SHA-256 digest to `revoked_certificate_sha256`; the deny list overrides matching public-key and certificate trust pins, so keep it narrow and audit every entry.
- `[torii.soranet_privacy_ingest]`: Guards for `/v1/soranet/privacy/{event,share}`. `enabled` must be `true` to expose the endpoints; `require_token` + `tokens` enforce the `X-SoraNet-Privacy-Token` (or `X-API-Token`) header, `allow_cidrs` restricts submitters by CIDR (empty list denies by default), and `rate_per_sec`/`burst` apply a token-bucket limiter. Rejects surface `401/403/429` with retry hints and labelled telemetry counters so operators can alert on abuse; see `specs/sorafs_authz_runbook.md` for the rollout checklist.

- `[sorafs.discovery]`: Canonical discovery toggle and capability allow-list. `discovery_enabled` defaults to `false` (Sora profiles such as `tests/fixtures/base.toml` enable it explicitly), `known_capabilities` ships with `["torii_gateway", "chunk_range_fetch", "vendor_reserved"]`, `replay_checkpoint_path` defaults to `sorafs_discovery/provider_advert_replay.to` relative to `torii.data_dir` (absolute paths remain absolute), and `replay_checkpoint_max_entries` defaults to the hard first-release maximum of 65,536. The checkpoint is mandatory when discovery is enabled and durably binds each admitted provider to its latest issuance timestamp and advert fingerprint; corruption fails closed. Enabling discovery, or configuring an admission directory, requires `[sorafs.discovery.admission]` with `envelopes_dir`, a non-empty `trusted_council_keys` array of canonical Ed25519 public keys, and a non-zero `signature_threshold` no greater than the number of distinct keys. Missing, duplicate, non-Ed25519, malformed, or unsatisfiable trust settings are startup errors; envelope-embedded keys are never trust roots. When discovery is disabled and no admission table exists, gateway admission remains deny-all rather than inventing a trust root. The directory loader accepts canonical `.to` envelopes plus its documented `README.md`, rejects symlinks and other entries, and bounds each envelope to 1 MiB and the registry to 4,096 entries. Rotate council keys by deploying an overlap policy that can still satisfy the threshold, re-signing active envelopes, then removing retired roots; removing a root immediately makes envelopes signed only by that key fail reload.
- `[sorafs.storage]`: Embedded SoraFS worker configuration. Key fields: `enabled`, `data_dir` (storage root), `max_capacity_bytes`, `max_parallel_fetches`, `max_pins`, `por_sample_interval_secs`, optional `alias`, and `governance_dag_dir` pointing at the public filesystem directory where signed governance artefacts are materialised. A configured Governance directory is an all-or-nothing production binding: it requires enabled storage, the publisher peer, signer handle/revision/policy digest, canonical strong Ed25519 public key, and the `[sorafs.storage.governance_dag_service]` checkpoint-store handle/revision/policy digest even when the public service is disabled. Runtime startup must inject the exact signer and sealed-CAS store; credentials and private keys are not accepted by `iroha_config`. The registry observes the signer metadata, issues a fresh domain-separated possession challenge, requests its signature, observes the metadata again even when signing fails, and only then verifies the returned Ed25519 signature against the configured key; substitution or drift takes precedence and fails startup. Unjournaled qualification changes fail closed. The crate-internal explicit rotation boundary requires both the predecessor and successor providers, retains the V1 publisher peer/key, and records a canonical dual-signed transition binding the exact sealed predecessor, current head/index, old/new public qualifications, and monotonic transition/archive heads. Its bounded signed qualification archives are installed and read back, then sealed by CAS and read back, before the live journal prefix is pruned. These files contain only public handles, qualifications, identities, digests, and signatures; they are not a credential store or an HSM implementation.

  `[sorafs.storage.governance_dag_service]` request authentication is an all-or-nothing public binding. The IPFS provider tuple includes `ipfs_authenticator_handle`, non-zero `ipfs_authenticator_revision`, canonical non-zero `ipfs_authenticator_policy_digest_hex`, and canonical strong-Ed25519 `ipfs_request_auth_public_key_hex`. `signed_http` head mode additionally requires the corresponding `head_*` tuple and `head_request_auth_public_key_hex`; `ipns` mode rejects every signed-head URL/authenticator field. `request_auth_max_envelope_lifetime_secs` defaults to `30` and is bounded to `1..=300`. `request_auth_max_future_skew_secs` defaults to `5`, is bounded to `0..=60`, and must remain strictly below the lifetime. These fields verify a bounded canonical signed-request envelope; no credential, token, private key, alias header, or provider diagnostic is accepted by configuration or emitted to the outbound request.

  On Linux and macOS, the stock launcher resolves the moderation quarantine PKCS#11/KMS wrapper, Governance signer/checkpoint/request-authenticator roles, and provider-ingest authenticated source, governed signer, sealed checkpoint, and finalized-archive retention roles through the bounded local broker. The moderation handshake pins the exact handle, revision, policy digest, and active public wrapping-key handle. Bounded canonical DEK wrap/unwrap operations reject malformed inputs, requalify those values around each external call, expose only the fixed `unavailable`/`rejected`/`stale-or-revoked`/`ambiguous` failure classes, and never carry provider credentials or diagnostics. `ambiguous` is valid only for a wrap that may have reached the provider; the poisoned session never replays it. Read-only unwrap uncertainty is `unavailable`. Every secret-bearing canonical, frame, request, response, and decoded wire buffer is overwritten on drop. A fixed operation discriminator applies the 80 KiB moderation ceiling before body allocation, length-prefixed reads allocate incrementally, and one shared inbound-byte budget prevents the eight admitted same-UID sessions from multiplying the 200 MiB general ceiling. Governance checkpoint and request-authenticator operations requalify the exact handle, revision, policy digest, and pinned public identity before and after access; the broker independently enforces checkpoint-generation monotonicity and exact CAS predecessors plus canonical descriptor, body, freshness, and replay bounds for signed requests. Ambiguous mutations terminate their authenticated session without replay. Each source fetch uses a dedicated authenticated connection and an independently bounded stream permit, so a stalled CAR reader does not consume unary broker capacity. The catalog pins the configured operation timeout, storage-capacity ceiling, source-count bound, and stream-concurrency bound. Canonical manifest/plan metadata is bounded separately from fixed 256 KiB payload frames; the reader admits EOF only after exact length, zero trailing bytes, payload digest, incremental transcript, and post-stream provider qualification all validate. Dropping a reader before that trailer closes and invalidates only its dedicated connection. Unsupported roles and unsupported platforms fail closed.

  `[sorafs.storage.provider_ingest_runtime.outbox]` defaults to a 160 MiB canonical checkpoint. `max_signed_transaction_bytes` is bounded to 64 KiB..=64 MiB. The checked checkpoint-capacity invariant reserves both an unsigned expected payload and the complete signed transaction for every active row, plus conservative canonical structural budgets for active rows, terminal tombstones, and checkpoint framing. Overflow or any aggregate above `checkpoint_max_bytes` is a startup error; the 192 MiB checkpoint ceiling cannot admit the retired 128 MiB transaction limit.

  The source tree now provides both the authenticated client and an injected broker-server library boundary; it does not provide an HSM, KMS, sealed-store, credential loader, or test backend. A deployment-owned broker launcher must inject every requested backend. Broker and client processes must run under the same effective service UID. The fixed socket (`/run/iroha/runtime-provider-broker-v1.sock` on Linux or `/private/var/run/iroha/runtime-provider-broker-v1.sock` on macOS) and its immediate directory must be owned by that UID; the directory must not be group/world writable, the socket mode is `0660`, and Unix peer credentials—not supplementary-group access—must match the pinned UID. Thus the shipped `User=iroha` validator service requires its broker service and runtime directory to use the same `iroha` account.

  The standalone Governance DAG launcher reads one bounded self-contained TOML file and rejects unresolved `extends`; embedded `irohad` uses its already-resolved configuration. The producer seals its canonical root and exact write-ahead intent in producer-specific store slots, while the public service uses separate checkpoint/intent slots. `[sorafs.storage.runtime]` bounds auxiliary state with `event_history_limit` (default `4096`), `state_entry_limit` (default `65536`, clamped to at least the history limit), `checkpoint_max_bytes` (default `64 MiB`), `proof_outcome_forwarder_interval_ms` (default `1000`), and `proof_outcome_max_attempts` (default `8`). The proof-outcome settings govern finalized height-and-block-hash reconciliation and bounded retry of one exact signed PDP/PoTR transaction. Before signing, the worker requires the runtime signer account to hold the exact provider-scoped `CanRecordSorafsProofOutcome` permission in finalized state, directly or through a role; a missing or differently scoped grant defers without consuming an attempt. Whenever storage is enabled, `[sorafs.storage.native_transaction_signers]` must contain distinct exact public bindings for proof-outcome, repair, reserve, and orderbook signers, and the launcher must inject all four matching live providers. This requirement is independent of the repair/reserve/orderbook new-work generation flags because storage keeps their durable forwarders active. Reserve and orderbook use the exact activation predicate `storage.enabled || <role>.enabled`: when both inputs are false, no worker task starts, so the role makes zero external signing, submission, or reconciliation progress. Opening the local `NodeHandle` may nevertheless update its durable checkpoint solely to normalize an interrupted signer-only `Signing` claim back to `Ready`, without refunding the attempt. The standard launcher never adapts the validator node key into any of these roles; it resolves configured providers through the authenticated runtime-provider broker, while an embedding may inject governed PKCS#11/HSM implementations through the role-specific `IrohaRuntimeDeps` setters. The `[sorafs.storage.adverts]` table exposes advert metadata (`stake_pointer`, `availability`, `max_latency_ms`, `topics`).
- `[sorafs.storage.evidence_viewer]`: Opt-in case-bound evidence-viewer policy. Enabled configuration requires the exact public handles, non-zero revisions, and canonical non-zero policy digests for the authoritative checkpoint store, WebAuthn verifier, rotating-grant authority, receipt signer, erasure boundary, and immutable compaction archive. The archive additionally pins a non-zero namespace id and Ed25519 verification key; `compaction_interval_ms` is bounded to `1000..=86400000` and `compaction_max_records` to `1..=1024`. The receipt-verification key and WebAuthn RP/origin policy are also mandatory. Credentials and private keys are not accepted. `checkpoint_path` is a bounded private local cache, never authority; the injected linearizable store's signed predecessor-bound CAS head is authoritative. The shutdown-aware Torii worker installs and reads back one exact service-signed artifact, verifies the archive signature, and only then prunes at most the configured record bound. Restart re-reads and verifies the current persisted archive artifact before serving. Enabled startup fails when any of the six dependencies is missing, substituted, stale, unavailable, or test-marked, while disabled configuration rejects every dormant runtime binding. - `[sorafs.storage.reputation_runtime]`: Opt-in committed projector and immutable finalized-query archive policy. `finalized_archive_max_record_bytes` defaults to `16777216` (16 MiB) for each canonical anchor or policy record, `finalized_archive_max_entries` defaults to `1000000` independently for each archive namespace, `finalized_archive_max_total_bytes` defaults to `68719476736` (64 GiB) across both namespaces, and `finalized_archive_max_kura_tip_lag_blocks` defaults to `2`. A lag of `0` requires the archive head to equal the Kura tip; the accepted range is `0..=10000`. When the runtime is enabled, `state_dir` must be an absolute private directory without `.` or `..` components. The archive root is always derived as `state_dir/finalized-reputation-archive-v1`; `finalized_archive_root` is not a user configuration key. The complete credential-free `journal_checkpoint_provider_handle`, exact V1 `journal_checkpoint_provider_revision`, and canonical non-zero `journal_checkpoint_provider_policy_digest_hex` binding are mandatory, and startup also requires the matching injected linearizable sealed-CAS provider. The provider seals the entire canonical journal checkpoint before the local cache is replaced; local fingerprints are never rollback authority. Record and per-namespace entry ceilings must be non-zero, the aggregate byte ceiling must cover at least one maximum-sized record, and the record ceiling must fit the target address space plus the checked four-times decode-allocation budget. Invalid bounds fail configuration loading without clamping. `finalized_archive_retention_enabled = true` additionally requires the complete credential-free `finalized_archive_retention_authority_handle`, non-zero `finalized_archive_retention_authority_revision`, and canonical non-zero `finalized_archive_retention_authority_policy_digest_hex` binding plus its deployment-injected sealed monotonic CAS adapter; partial, stale, test-marked, or dormant fields fail startup. Enabling this adapter does not select or schedule a prefix. Retention runs only for the monotonic digest-linked `sorafs_reputation_finalized_archive_retention_request_v1` custom parameter submitted in a caller-signed, `CanSetParameters`-authorized transaction, and the target must be an exact committed ancestor of its authorizing block. The daemon requires a zero-gap State/Kura/archive projection, refreshes the same request before approval, and requires exact CAS readback before checkpoint publication or deletion. There is no automatic age/capacity policy or process-local authority. While the runtime is disabled, all archive-policy values must remain at their exact defaults; non-default dormant policy claims are rejected.

  **SM rollout checklist.** The `iroha_config` layering (`defaults` → `user` → `actual`) allows staged rollouts:
  1. **Build validation.** Compile binaries with `--features sm` (and `sm-ffi-openssl` only if the preview backend is required). Without the feature flag the node rejects `sm2` in `allowed_signing`.
  2. **Configuration propagation.**
     - Update `crypto.allowed_signing` to include `sm2` (keep the list lexicographically sorted) and set `crypto.default_hash = "sm3-256"`.
     - Override `crypto.sm2_distid_default` with the distinguishing identifier mandated by your policy (e.g., the ISO/TC 68 value for your organisation).
  3. **Genesis alignment.** Regenerate genesis manifests via `kagami genesis generate --consensus-mode <mode>` (use `--allowed-signing sm2 --default-hash sm3-256` if you need overrides) so the `parameters` blocks and injected metadata mirror the config snapshot; commit them to version control alongside the updated TOML.
  4. **Telemetry & admission smoke tests.** Before turning on traffic, run `cargo test -p iroha_crypto --features sm` and the SM integration matrix scripts, then verify `/status` exposes `crypto.sm_helpers_available = true` and that Torii rejects SM2 signatures when `sm2` is absent from `allowed_signing`.
  5. **Rollback plan.** Document how to revert to Ed25519-only mode (remove `sm2` from `allowed_signing`, restore `default_hash = "blake2b-256"`) and confirm hosts drop in-flight SM transactions deterministically.

Notes
- Acceleration is automatic by default. Backends run golden self-tests on first use and disable themselves at runtime if a mismatch is detected; the VM falls back to scalar/SIMD and remains bit-identical across hardware.
- Prefer editing `peer.template.toml`-style files and extending them in deployment. Runtime behavior is configured via `iroha_config`; environment variable overrides exist for developer tooling but should not be relied on for operator workflows.
