# Configuration Overview

This page summarizes the top-level sections of the Iroha configuration file (TOML) and what each controls. For a concrete template, see `specs/references/peer.template.toml`.

Defaults first: configuration values are curated for typical Iroha blockchain deployments. In most cases, you can run with the defaults unchanged. Only adjust settings when you have a specific operational need (e.g., custom ports, strict rate limits, or known network constraints).

- Sora-specific sections (`sorafs.*`, multi-lane `nexus.*`) require starting the daemon with `iroha3d --sora …` (or exporting `IROHA_SORA_PROFILE=1`). Without the flag the loader rejects configurations that enable those features.
- Nexus routing is mandatory in the first release and has no availability switch; `enabled` is an unknown key in `[nexus]`. The canonical one-lane catalog uses the transaction-aware `ConfigLaneRouter`; multi-lane/Sora topology overrides additionally require the Sora profile and authenticated NPoS consensus mode.
- `[common]`: Chain identity (`chain`), node key pair, trusted peers, and the i105 display discriminant (`chain_discriminant`). `chain` is exact, case-sensitive ASCII of 1–128 bytes; it starts and ends with an alphanumeric and otherwise permits only alphanumerics plus `.`, `_`, `:`, and `-`. Assign a unique value to every distinct deployment/replay domain. `AccountId` and `AccountAddress` are universally scoped and domainless; domain routing uses explicit `DomainId` and account-alias records, never a node-local default label.
- Identity separation: `public_key` plus exactly one of `private_key` or `private_key_file` forms the node's transport + consensus identity and must be BLS‑Normal for validator nodes. Production profiles use `private_key_file`; the file is read once through a bounded descriptor, must contain one canonical key, and on Unix must not grant group/other access. The same exact-one-source rule applies to the dedicated SoraNet transport key (`soranet_transport_private_key` or `_file`). Validator identities must appear in `trusted_peers` alongside a valid PoP in `trusted_peers_pop`. Trusted peers without PoPs are network-trusted observers and are excluded from consensus. Config parsing rejects invalid PoPs or PoP maps that reference keys outside `trusted_peers`. `crypto.allowed_signing`/`allowed_curve_ids` gate transaction admission and non-consensus account controllers; BLS validator accounts are accepted even if `allowed_signing` omits BLS. Add `bls_normal` to `allowed_signing` only when you intend to accept BLS‑signed transactions.
- `[genesis]`: Location of the operator-provisioned signed genesis file, the public key used to verify it, and exactly one mandatory trust-root source: inline `expected_hash` or canonical `expected_hash_file`. The file's exact content is one checked `hash:<64 uppercase hex>#<CRC16>` NetworkId literal followed by one LF; CRLF and unterminated aliases are rejected. Production templates use `/run/iroha/genesis.expected_hash`; the same Kagami-generated file feeds client `network_id_file`, so the two security domains cannot drift. The referenced manifest carries parameter families such as `transaction.max_signatures`, `transaction.max_instructions`, `transaction.ivm_bytecode_size`, `transaction.max_tx_bytes`, `transaction.max_decompressed_bytes`, and `transaction.max_time_to_live_ms`; update the manifest when tightening admission limits. `max_time_to_live_ms` defaults to one day and is the on-chain ceiling for every signature-bound transaction TTL. Configuration normalization resolves the expected hash independently of the artifact before it reads a genesis body from the local file or Kura. A configured artifact must match the hash. Genesis must have exactly one block signature at index zero, signed by `public_key`; its first transaction authority and exact header hash must match the same resolved anchor. A fresh node also needs the complete local signed artifact; a restarting node may use the matching body already stored in Kura. Empty storage with only a hash fails because Iroha has no peer genesis retrieval protocol. Audited provisional snapshot bootstrap is the only independent startup trust root and is governed separately by `snapshot.bootstrap`. See `specs/startup_trust_roots.md` for the startup ordering and operator checklist.
- `[network]`: P2P addresses, gossip periods/sizes, DNS refresh, bounded queue capacities, mandatory TLS 1.3 transport, optional QUIC, and automatic SCION preference when both peers advertise support. `network.address` is the authenticated TLS listener; there is no plaintext listener or retry knob. Deferred outbound sends are bounded by age, per-peer count/stream-wire bytes, and the true-total `network.deferred_send_max_bytes_total` cap (128 MiB by default). The total owner keeps an additive authenticated-consensus safety reserve; ordinary traffic cannot consume it.
- Consensus ingress guardrails: `network.consensus_ingress_rate_per_sec`/`consensus_ingress_burst` cap per-peer consensus/control frames (`null` disables), `network.consensus_ingress_bytes_per_sec`/`network.consensus_ingress_bytes_burst` cap payload volume, `network.consensus_ingress_critical_rate_per_sec`/`consensus_ingress_critical_burst` and `network.consensus_ingress_critical_bytes_per_sec`/`network.consensus_ingress_critical_bytes_burst` apply dedicated caps to liveness-critical messages (fallback to the standard caps when both critical caps are unset; penalty cooldowns apply in that fallback), and `network.consensus_ingress_penalty_threshold` + `network.consensus_ingress_penalty_window_ms` + `network.consensus_ingress_penalty_cooldown_ms` temporarily suppress peers that exceed the standard caps. Revision-4 `Proposal`, `Vote`, `QuorumCertificate`, timeout, `PayloadManifest`, `PayloadChunk`, body/certificate requests, `CommitCertificateResponse`, and global threshold-beacon partial signatures use the critical ingress policy; `CertifiedBodyResponse` and BlockSync traffic use the bulk policy. These node-local resource caps do not alter the signed full-committee quorum or mandatory RS16 protocol.
- `[ivm]`: Runtime presentation settings. Guest stack geometry is fixed by `IvmStackPolicy::V1`; node configuration cannot override it.
- `[pipeline]`: Transaction pipeline parallelism and caches. `pipeline.workers` (0 = auto) sets the worker pool used for the stateless pre-pass, access derivation, and overlay construction; `pipeline.stateless_cache_cap` bounds the stateless validation cache (0 disables it) so identical transactions can skip repeat pre-pass checks until TTL/clock-drift windows expire.
- `[tiered_state]`: Hot/cold WSV tiering knobs (`enabled`, `hot_retained_keys`, `hot_retained_bytes`, `hot_retained_grace_snapshots`, `cold_store_root`, `da_store_root`, `max_snapshots`, `max_cold_bytes`). If `cold_store_root` is unset, snapshots are stored under `da_store_root`; changing either root resets tiering metadata.
- `[concurrency]`: Native thread-pool sizing and stack budgets for Tokio runtime/blocking threads, scheduler/prover workers, and Sumeragi helpers. `tokio_stack_bytes` defaults to 8 MiB and is validated within 8–64 MiB. These operational settings do not alter guest-visible IVM memory geometry. The V1 guest policy always uses a 64 KiB floor, 4 MiB ceiling, four stack bytes per gas unit, and 16-byte alignment.
- `network.peer_gossip_period_ms` (default: `1000`ms) also governs the topology refresh cadence. The `IROHA_P2P_TOPOLOGY_UPDATE_MS` env override is now ignored; adjust the config field instead. Peer-address gossip backs off when idle up to `network.peer_gossip_max_period_ms`, and block-sync sampling backs off up to `network.block_gossip_max_period_ms`. Gossip periods (`block_gossip_period_ms`, `block_gossip_max_period_ms`, `transaction_gossip_period_ms`, `peer_gossip_period_ms`, `peer_gossip_max_period_ms`), `idle_timeout_ms`, and `reply_writer_flush_timeout_ms` are clamped to a minimum of 100ms to avoid tight loops. `reply_writer_flush_timeout_ms` defaults to 30 seconds and is the base deadline for one exact reply's peer-writer occurrence; only an observed timeout increases that item's next deadline, while a successful full flush resets it.
- SCION transport selection is capability-driven and automatic: peers advertise `scion_supported` in handshake/trust metadata and peer gossip, and outbound dialing prefers SCION-capable paths only when both sides advertise support. Peers without SCION capability use QUIC when requested and otherwise mandatory TLS; raw TCP is never a peer transport. No `network.scion_*` keys exist; retired keys are rejected as unknown fields.
- `network.trust_gossip` (default: `true`) advertises support for TrustGossip frames. Setting it to `false` negotiates the capability off at handshake time, dropping TrustGossip messages while leaving peer-address gossip intact. Drops are tagged via `p2p_trust_gossip_skipped_total{direction,reason}` so operators can spot opt-outs or peers that refused the capability.
- Trust scoring knobs under `[network]` (`trust_decay_half_life_ms`, `trust_penalty_bad_gossip`, `trust_penalty_unknown_peer`, `trust_min_score`) apply in permissioned overlays: trust frames that reference peers outside the active topology incur the unknown-peer penalty, increment `p2p_trust_penalties_total{reason="unknown_peer"}`, and senders below `trust_min_score` are ignored until decay recovers. Public/NPoS overlays skip the unknown-peer penalty so trust gossip remains open.
- Transaction gossip tuning: `network.transaction_gossip_drop_unknown_dataspace` drops batches for dataspaces missing from the lane catalog; `network.transaction_gossip_restricted_target_cap` caps restricted fanout (defaults to the full commit topology); `network.transaction_gossip_public_target_cap` caps public-lane fanout (default 16, set `null` for broadcast); `network.transaction_gossip_public_target_reshuffle_ms` and `network.transaction_gossip_restricted_target_reshuffle_ms` control how often target selection reshuffles per plane (defaults to `transaction_gossip_period_ms`, clamped to ≥100ms); `network.transaction_gossip_resend_ticks` sets how many gossip periods elapse before re-sending the same transactions (higher reduces duplicate traffic); `network.transaction_gossip_restricted_fallback` (`drop` | `public_overlay`) controls whether restricted gossip falls back to online peers when the commit topology is empty; and `network.transaction_gossip_restricted_public_payload` (`refuse` | `forward`, default `refuse`) currently refuses to leak restricted payloads when only the public overlay is available (forwarding is blocked until encrypted transport lands). Telemetry surfaces the drop/forward policy via gauges and `/status.tx_gossip` entries (caps, targets/peers, fallback surface, reason/outcome) so operators can alert on blocked or rerouted batches.
- `network.soranet_handshake.pow`: Mandatory challenge configuration for SoraNet admission; there is no `required` switch. Fields: `difficulty`, `max_future_skew_secs`, `min_ticket_ttl_secs`, `ticket_ttl_secs`, `revocation_store_capacity`, `revocation_store_ttl_secs`, and `revocation_store_path`. The replay store controls how many consumed raw or signed ticket fingerprints are retained on disk and how long they remain authoritative for replay detection; its TTL must be at least `max_future_skew_secs` so every accepted ticket stays consumed through expiry.
- `network.soranet_handshake.pow.puzzle`: mandatory Argon2 puzzle settings. The first-release resource corridor is `memory_kib = 4096..=131072`, `time_cost = 1..=8`, `lanes = 1..=16`, and static `difficulty = 1..=32` (default `6`). The standalone relay uses the same single configured difficulty and rejects an `adaptive` key as unknown. Runtime updates outside those bounds are rejected atomically. Handshake security policy is node-local operator configuration and is never accepted from or propagated through P2P messages.
- `network.soranet_handshake.kem_suite`: Optional textual override (`"mlkem512"`, `"mlkem768"`, or `"mlkem1024"`; `kyber*` aliases are also accepted) for the ML-KEM profile used during the SoraNet handshake. When set it supersedes `kem_id`. The bundled default capability vectors are synchronized with this selection and with `descriptor_commit`; custom vectors must explicitly advertise the selected KEM on both roles and make the relay `snnet.transcript_commit` value match the configured descriptor commitment.
- `[sumeragi]`: First-release revision-4 node settings are limited to the local participation `role`, finite candidate limits under `block`, bounded ingress/adapter resources under `queues` and `limits`, node-local durable budgets under `storage`, and consensus signing-key policy under `keys`. `storage.body_store_max_bytes_per_height` defaults to 1 GiB, must hold at least one maximum checksummed body frame, and bounds final body bytes retained for one active height without changing the shared protocol fingerprint. Consensus mode, cadence, exact `3f + 1` committee, leader selection, quorum, and mandatory RS16 DA layout come from signed genesis and each `HeightContext`. One crate-internal `LifecycleCoordinator` with `LifecycleLedgerV1` owns production scheduling and recovery; it has no enable/disable knob. Retired V1 tables such as `advanced`, `collectors`, `da`, `debug`, `gating`, `npos`, `persistence`, and `recovery`, along with local protocol/timing fields and fault switches such as `conflicting_ready_mask` and `duplicate_inits`, are rejected rather than ignored.
- `[torii]`: Public API server settings such as listen address, request size caps, and query store parameters.
- `[torii.faucet]`: Optional server-signed account creation/funding mutation. If the
  table is present, `pow_difficulty_bits` must be non-zero; the default is `18`,
  while an operator may explicitly choose a lower positive value for a bounded
  development deployment. The public puzzle uses
  first-release `scrypt-leading-zero-bits-v1` algorithm and
  `iroha:accounts:faucet:pow:v1` challenge domain, carries the canonical exact
  `NetworkId` and I105 chain discriminant, and hashes the raw 32-byte
  `NetworkId` immediately after that domain. Claims always require the
  advertised anchor and nonce; pre-release labels are rejected, and the route
  is a protocol-authenticated mutation, not a public read.
- `torii.api_tokens` supplies the credential allow-list for Torii API-token
  authentication. `torii.require_api_token` applies that allow-list to the
  whole listener. It is not route-level authority: ISO 20022, webhook
  management, and SoraFS stream-token issuance require fresh exact-network
  operator signatures before request-body decoding.
- `torii.api_rate_limit_bypass_cidrs`: Effective client CIDRs that bypass
  Torii's API request-rate limit only. Broad subnets are permitted because this
  field grants no authentication, internal-read, or target-account routing
  privilege; body-size, admission, and credential checks still apply.
- `torii.internal_api_trusted_cidrs`: Exact effective transport source hosts
  trusted for unprojected `/v1/internal/*` reads and unsigned target-account
  routing. Entries must be IPv4 `/32` or IPv6 `/128`; broader networks are
  rejected during configuration parsing. The default trusts only
  `127.0.0.1/32` and `::1/128`. When a request arrives through a configured
  trusted proxy, this policy is evaluated against Torii's validated effective
  client address.
- `torii.transport.trusted_proxy_cidrs`: Explicit proxy transport hosts
  (`/32` for IPv4 or `/128` for IPv6) whose
  `X-Forwarded-For` chain Torii may use for client-IP rate limits and CIDR
  policy. Network-wide and wildcard trust ranges are rejected during
  configuration parsing. A trusted proxy must overwrite the header or append
  its observed source address. Torii walks the chain from the transport side,
  ignores any attacker-selected prefix before the first untrusted address,
  rejects malformed or longer-than-32-hop chains, and never accepts the
  internal `x-iroha-remote-addr` header from the network.
- `[torii.transport.http]`: HTTP/1 socket and request-head limits enforced
  before request middleware. `max_connections` defaults to `1024`, while
  `max_connections_per_ip` defaults to `64` and cannot exceed the global
  limit. `header_read_timeout_ms` and `write_timeout_ms` default to `10000`
  and `30000` and must be non-zero. `max_headers` defaults to `100` and is
  capped at `1024`; `max_header_bytes` defaults to `65536` and must remain in
  the inclusive `8192..=1048576` range.
- `torii.preauth_allow_cidrs`: Explicit source hosts that bypass the
  pre-authentication resource gate. It accepts only IPv4 `/32` and IPv6 `/128`
  entries, plus `127.0.0.0/8` as the local-host loopback range; broad remote
  subnets cannot disable pre-authentication admission.
- `torii.preauth_ban_capacity`: Maximum active temporary pre-authentication
  bans retained in memory (default: `4096`). The store purges expired entries
  first and evicts the earliest-expiring live entry at capacity, keeping
  attacker-controlled source addresses from growing the ban store without
  bound.
- `[torii.transaction_ingress]`: Physical transaction-submission resource corridor.
  `max_concurrent_compute_jobs` (default: `4`) bounds blocking transaction
  admission work: batch-envelope and transaction decode, canonicalization,
  signature verification, routing, and atomic queue admission across single,
  entrypoint, and batch submission routes. Torii fails fast when all slots are
  occupied, and each owned slot remains in the physical worker until it exits
  even if the HTTP request times out or disconnects.
  `max_batch_transactions` (default: `512`) is the exact top-level transaction
  count accepted by `/v1/pipeline/transactions/batch`. Torii authenticates and
  enforces encoded and declared-decoded byte limits before compute admission,
  then uses Norito's authoritative sequence decoder to reject count overflow
  and exact queue pressure before decoding any signed transaction payload.
  `verified_source_max_concurrent_compiles` (default: `1`, V1 maximum: `4`)
  bounds complete Kotodama compiler working sets for verified-source jobs. Its
  fail-fast permit is acquired before Torii polls or decodes the signed request
  body and moves into the blocking compiler worker, so disconnecting a client
  cannot admit replacement compilation while the detached worker still runs.
  `verified_source_body_read_timeout_ms` (default: `10000`) is the absolute
  deadline for completing that already-admitted bounded body read.
- `torii.receipt_public_key` / `torii.receipt_private_key` (optional): Dedicated key pair used to sign transaction and DA submission receipts. If omitted, `irohad` deterministically derives a domain-separated Secp256k1 receipt key from the node identity, so receipts remain verifiable across ordinary restarts without reusing the node key. Set both values when receipt identity must remain independent of node-key rotation; BLS keys are rejected here—use Ed25519 or Secp256k1. Torii refuses to start when its durable DA receipt log cannot be opened or verified, rather than starting a permanently unusable DA endpoint.
- `[torii.kagemusha_commands]`: App-facing typed Kagemusha submission policy. An enabled service requires exactly one of `private_key` or `private_key_file`; production profiles use the bounded owner-held file. The file is opened once, must contain one canonical Ed25519 or Secp256k1 key, and on Unix must deny group/other access. The renderer writes this signer as a mode-`0600` runtime sidecar and emits only its path.
- `[torii.operator_signatures]`: Mandatory exact-request authentication for every route cataloged as `OperatorSignature`. `enabled` must remain true for those routes to be usable; disabling it fails them closed rather than falling back to sessions or bearer tokens. `allow_node_key` and `allowed_public_keys` define the signer allowlist, while `max_clock_skew_secs`, `nonce_ttl_secs`, and `replay_cache_capacity` bound freshness and replay state. `body_read_timeout_ms` (default: `10000`) is the absolute limit for collecting each bounded raw body before verification; expiry releases admission and returns `408 Request Timeout`. Each signature binds the runtime `NetworkId`, method, path, sorted query, raw body hash, timestamp, and nonce.
- `[torii.operator_auth]`: Optional WebAuthn/mTLS second factor for operator endpoints. When `enabled`, its session/token and mTLS checks are required in addition to the exact operator request signature; they never substitute for it. `require_mtls` expects `X-Forwarded-Client-Cert` from an edge peer in `mtls_trusted_proxy_cidrs`. Every trusted edge must remove any inbound copy of that header and insert it only after authenticating the client certificate; Torii deliberately treats the configured edge as the certificate-authentication boundary. `token_fallback` controls second-factor bootstrap token usage (`disabled|bootstrap|always`), `token_source` selects `operator|api|both`, and `tokens` configures the operator-token allowlist. `rate_per_minute`/`burst` apply to auth attempts, while `lockout.{failures,window_secs,duration_secs}` controls temporary lockouts. `webauthn` is required when `enabled = true` and configures `rp_id`, `rp_name`, `origins`, `user_id`, `user_name`, `user_display_name`, `challenge_ttl_secs`, `session_ttl_secs`, `require_user_verification`, and `allowed_algorithms`. Credentials persist under `<torii.data_dir>/operator_auth/operator_webauthn.json`. When `token_fallback = "bootstrap"`, tokens are accepted only until the first credential is enrolled; after that operators must log in and send `x-iroha-operator-session` alongside every exact request signature.
- `torii.events_buffer_capacity` (default: `10000`): Broadcast channel size used for `/v1/events/sse` and webhook enqueuing. Lower the value to bound memory/backpressure when subscribers lag.
- `torii.ws_message_timeout_ms` (default: `10000`): WebSocket message timeout (read/write) for Torii event/block streams; increase it for slow clients or high-latency links. The initial subscription read uses one absolute deadline: Ping/Pong frames are accepted but do not renew it.
- `torii.app_api.*`: Pagination/backpressure defaults for JSON convenience endpoints. `default_list_limit` seeds `limit` when omitted, `max_list_limit` and `max_fetch_size` bound page/fetch sizes, and `rate_limit_cost_per_row` controls how much each requested row costs under the app API rate limiter.
- `[torii.recipient_lookup]`: Privacy-minimized retail routing and bank-name lookup. `policy_id` (default `cbuae_aed_sbp_pkr`) selects the governed FX corridor policy and `requests_per_minute` (default and maximum `30`) applies a dedicated per-signer limiter shared by `POST /v1/retail/recipients/route` and `POST /v1/retail/recipients/lookup`. Both endpoints require canonical request signing, an existing signer, an enabled owner-funded corridor policy, and a positive signer balance in that policy's source asset/dataspace. Settlement releases the destination asset only from the exact `NetworkId`-derived protocol escrow and requires exact fresh oracle evidence plus the signed expected output. `request_timeout_ms` bounds configured upstream bank calls and each `[[torii.recipient_lookup.routes]]` entry supplies an exact `fi_id` (`hbl.sbp` or `ubl.sbp`), `base_url`, and private `bearer_token`. `/route` returns only `{account_id, alias_fqn, fi_id}`; `/lookup` additionally contacts the selected bank route. Fee sponsorship is separate: account-signed `POST /v1/fee-sponsor-programs/by-id` reads one exact lifecycle record, while account-signed `POST /v1/fees/quote` evaluates the exact unsigned transaction payload through the canonical admission router. Neither endpoint synthesizes a fallback program or payer.
- `torii.webhook.*`: Delivery/backoff tuning for the webhook worker. `queue_capacity` caps on-disk pending deliveries (default: `10000`), `max_attempts` bounds retries (default: `12`), `backoff_initial_ms`/`backoff_max_ms` set the exponential retry window (defaults: `1000`/`60000`), and `{connect,write,read}_timeout_ms` configure HTTP timeouts for delivery attempts. Listing, creating, and deleting webhook registrations requires a fresh allow-listed exact-network operator request signature bound to the method, path, sorted query, and raw body.
- `torii.push.*`: Best-effort account activity push delivery. `enabled` starts a Torii-only worker that watches committed blocks, stores device registrations under `<torii.data_dir>/push/`, queues minimal account-activity payloads, and retries provider delivery without affecting consensus. Device registration and deletion bind the exact body and route to an existing account through canonical signed-request headers before changing the local registry. `rate_per_minute`/`burst` limit device registration, `max_topics_per_device` bounds stored topic labels, and `connect_timeout_ms`/`request_timeout_ms` bound FCM/APNs HTTP attempts. FCM uses HTTP v1 exclusively and requires `fcm_project_id` plus `fcm_service_account_path`. APNs uses `.p8` token authentication exclusively and requires `apns_environment` (`sandbox` or `production`), `apns_topic`, `apns_team_id`, `apns_key_id`, and `apns_private_key_path`; `apns_endpoint` is only an override for tests or private deployments. Retired legacy credential fields are rejected as unknown configuration.
- `torii.da_ingest.*`: Replay cache and manifest spool configuration for the DA pipeline.
  - `max_concurrent_compute_jobs` (default: `1`) bounds physical signature verification,
    normalization, chunking, RS16, manifest, and PDP work. These phases run through
    `spawn_blocking` only after acquiring an owned semaphore permit; the worker retains that
    permit through physical completion even if the originating HTTP request is cancelled.
  - `replay_cache_capacity` (default: `4096`) independently bounds committed sequence
    fingerprints and in-flight reservations inside each `(lane, epoch)` window (at most twice the
    configured value while ingests are active). `replay_cache_max_lane_epochs` (default: `1024`)
    is the independent global bound on distinct windows across memory and durable cursor recovery. DA receipt
    Prometheus series use bounded outcome labels and lane-only dimensions; the current epoch is a
    gauge value rather than an epoch label, and retired-lane series are pruned with lane lifecycle
    state.
    Admission fails closed when that global capacity is full; startup also fails closed if a
    checkpoint or journal exceeds it.
  - `replay_cache_store_dir` (default: `./storage/da_replay`) contains a bounded append journal and
    its canonical checkpoint. Cursor advances append and sync one checksummed record; after at most
    `replay_cache_max_lane_epochs` records Torii checkpoints the bounded map and truncates the
    journal. A torn final frame is truncated during recovery, while a corrupt complete frame,
    symlink, or conflicting checkpoint aborts startup rather than silently discarding replay state.
  - `replay_cache_ttl_secs` (default: `900`) controls in-memory fingerprint retention and
    `replay_cache_max_sequence_lag` (default: `4096`) rejects old sequences behind a window's
    high-water mark. Durable high-water marks remain authoritative across restarts.
  - `telemetry_cluster_label` (optional): Sets the `cluster` label emitted on Taikai ingest/viewer metrics so dashboards can distinguish environments (e.g., `region-a` vs `staging`).
    Set `governance_metadata_key_hex` to a 32-byte ChaCha20-Poly1305 key when you need
    Torii to seal governance-only metadata; pair it with `governance_metadata_key_label`
    (a short identifier such as `"primary"`) so encrypted entries advertise which key
    produced the ciphertext. Torii encrypts cleartext governance metadata automatically
    and refuses manifests whose pre-encrypted payloads carry missing or mismatched labels.
    The nested `replication_policy` table defines the enforced `RetentionPolicy` per
    blob class (see `specs/da/replication_policy.md`). Override `default_retention`
    to change the baseline hot/cold windows and add entries under
    `replication_policy.overrides` (e.g., `class = "taikai_segment"`) to tighten
    specific classes; Torii rewrites caller-supplied manifests to match these values
    and rejects mismatched envelopes.
  - `debug_match_filters` (default: `false`) enables deterministic filter-debug traces formerly gated by the `TORII_DEBUG_MATCH` environment toggle. Keep this off in production.
- `torii.iso_bridge.max_body_bytes`: Maximum request body accepted by every ISO 20022 submission endpoint (default: `1 MiB`). Torii applies this limit before XML extraction and also caps it at the listener-wide `torii.max_content_len`; enabled bridges reject a zero limit at startup.
- `torii.query_fanout_max_retained_bytes`: Aggregate memory reserved for signed-query ingress and cross-dataspace fanout (default: `64,000,000`). Torii reserves one quarter for four complete pre-body slots and the remainder for complete fanout working sets. Each ingress slot accounts five simultaneously live variable representations: the decoded signed request, its canonical frame, a nested routing-scope decode, that scope's canonical frame, and serializer scratch. A slow request body therefore cannot occupy the fanout execution slot, while ingress-to-fanout promotion acquires the full fanout reservation before releasing ingress. Route bodies and final proxy snapshots use smaller phase-derived limits. The fanout slot weight is derived from fixed routing state plus the configured content limit; when the aggregate pool cannot cover that whole listener limit, only the signed-query body allowance is reduced. Small positive listener limits therefore remain valid instead of being rejected by an arbitrary minimum. V1 rejects a zero content limit, an aggregate pool below 20,000,000 bytes, a proxy body above its 64,000,000-byte protocol ceiling, or values that do not fit the platform address space.
- `torii.app_api_routed_read_body_read_timeout_ms`: Absolute deadline for collecting one admitted App API routed-read body (default: `10000`; must be non-zero). The complete 45-route request corridor and memory ownership proof are summarized in [`docs/source/torii_app_routed_read_admission.md`](../../docs/source/torii_app_routed_read_admission.md).
- `[torii.tx_history]`: Optional wallet-history visibility policy. `mandatory_aliases_path` names a direct regular JSON file whose object keys are canonical configured dataspaces and whose values are arrays of canonical account aliases in that same dataspace. `mandatory_aliases_max_file_bytes` defaults to—and in V1 cannot exceed—`16 MiB`; prepared Kagami deployments use the same configured maximum when copying the runtime artifact. Bounded canonical DEK wrap/unwrap operations reject malformed inputs, requalify those values around each external call, expose only the fixed `unavailable`/`rejected`/`stale-or-revoked`/`ambiguous` failure classes, and never carry provider credentials or diagnostics. `ambiguous` is valid only for a wrap that may have reached the provider; the poisoned session never replays it. Read-only unwrap uncertainty is `unavailable`. Every secret-bearing canonical, frame, request, response, and decoded wire buffer is overwritten on drop. A fixed operation discriminator applies the 80 KiB moderation ceiling before body allocation, length-prefixed reads allocate incrementally, and one shared inbound-byte budget prevents the eight admitted same-UID sessions from multiplying the 200 MiB general ceiling. Governance checkpoint and request-authenticator operations requalify the exact handle, revision, policy digest, and pinned public identity before and after access; the broker independently enforces checkpoint-generation monotonicity and exact CAS predecessors plus canonical descriptor, body, freshness, and replay bounds for signed requests. Transport ambiguity and typed mutation ambiguity retire the current authenticated session without replay. For evidence-viewer transparency CAS only, the client attempts a fresh same-UID, exact-catalog session solely so the producer can requalify the publisher and load its authoritative signed head; the mutation itself is never replayed. Each source fetch uses a dedicated authenticated connection and an independently bounded stream permit, so a stalled CAR reader does not consume unary broker capacity. The catalog pins the configured operation timeout, storage-capacity ceiling, source-count bound, and stream-concurrency bound. Canonical manifest/plan metadata is bounded separately from fixed 256 KiB payload frames; the reader admits EOF only after exact length, zero trailing bytes, payload digest, incremental transcript, and post-stream provider qualification all validate. Dropping a reader before that trailer closes and invalidates only its dedicated connection. Unsupported roles and unsupported platforms fail closed.

A deployment-owned broker launcher must inject every requested backend. Broker and client processes must run under the same effective service UID.   **SM rollout checklist.** The `iroha_config` layering (`defaults` → `user` → `actual`) allows staged rollouts:
  1. **Build validation.** Compile binaries with `--features sm` (and `sm-ffi-openssl` only if the preview backend is required). Without the feature flag the node rejects `sm2` in `allowed_signing`.
  2. **Configuration propagation.**
     - Update `crypto.allowed_signing` to include `sm2` (keep the list lexicographically sorted) and set `crypto.default_hash = "sm3-256"`.
     - Override `crypto.sm2_distid_default` with the distinguishing identifier mandated by your policy (e.g., the ISO/TC 68 value for your organisation).
  3. **Genesis alignment.** Regenerate genesis manifests via `kagami genesis generate --consensus-mode <mode>` (use `--allowed-signing sm2 --default-hash sm3-256` if you need overrides) so the `parameters` blocks and injected metadata mirror the config snapshot; commit them to version control alongside the updated TOML.
  4. **Telemetry & admission smoke tests.** Before turning on traffic, run `cargo test -p iroha_crypto --features sm` and the SM integration matrix scripts, then verify `/status` exposes `crypto.sm_helpers_available = true` and that Torii rejects SM2 signatures when `sm2` is absent from `allowed_signing`.
  5. **Rollback plan.** Document how to revert to Ed25519-only mode (remove `sm2` from `allowed_signing`, restore `default_hash = "blake2b-256"`) and confirm hosts drop in-flight SM transactions deterministically.

- `[accel]`: Hardware acceleration settings for IVM and helpers.

Notes
- Acceleration is automatic by default. Backends run golden self-tests on first use and disable themselves at runtime if a mismatch is detected; the VM falls back to scalar/SIMD and remains bit-identical across hardware.
- Prefer editing `peer.template.toml`-style files and extending them in deployment. Runtime behavior is configured via `iroha_config`; node startup with `--config` ignores ambient environment-variable aliases so a checked or integrity-bound TOML artifact cannot be rewritten by the launcher environment. The no-config deterministic-development path and tests may still exercise explicit environment inputs.
