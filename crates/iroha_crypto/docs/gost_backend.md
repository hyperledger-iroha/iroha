# GOST implementation and qualification

Iroha exposes five GOST R 34.10-2012 algorithm identities: CryptoPro 256-bit parameter sets A/B/C from RFC 4357 and 512-bit parameter sets A/B from RFC 7836. The algorithm discriminants, labels and canonical key/signature bytes are defined in `src/algorithm.rs`, `src/multihash.rs` and `src/signature/gost.rs`. Public points encode little-endian x followed by y; signatures encode little-endian r followed by s. These 256-bit labels must not be interpreted as the same-letter TC26 256-bit parameter identities.

The [parameter and verification owner specification](../../../specs/crypto/gost_parameter_owner.md) identifies the canonical literal owner, encoding, full verification relation and resource obligations. The production implementation has one fixed-width verification relation. Ordinary, typed, admission and explicit owned-key verification all use it. There is no second verifier, compatibility decoder or proposed backend rollout switch. The `gost` Cargo feature selects the algorithm family; it does not select alternate mathematical relations.

## Arithmetic and allocation ownership

`src/signature/gost/constant_time.rs` implements fixed-width Montgomery field operations and Jacobian point arithmetic using `crypto-bigint`. The borrowed verifier checks exact widths and canonical coordinates before fixed-integer conversion, validates the curve equation, constrains signature scalars, computes the Streebog-derived scalar relation, and rejects an infinite result before comparing affine x modulo the subgroup order. All admitted parameter literals have one owner shared with signing.

Borrowed public validation and verification retain no heap-backed decoded key and bypass decoded-key caching. Compact construction still allocates its canonical payload. The explicit owned `gost::PublicKey` facade retains one payload allocation and invokes the same verification relation. Public malformed-key diagnostics still materialize String allocations, followed by further wrapping at some Norito boundaries. **TODO: fund these error allocations and include inline fixed scratch in execution stack admission before declaring complete resource custody.** A successful decode descriptor of zero parser heap units is not an error-path or whole-Crypto funding claim.

Signing, nonce construction, private-key parsing, public derivation and key generation still use `num_bigint::BigUint` and allocated byte buffers. Fixed point operations adapt those outer values through allocating conversion helpers. Production signing incorporates OS entropy into the HMAC-Streebog nonce process and rejects unavailable/all-zero entropy; tests can supply explicit entropy or use the internal deterministic path. Zeroization of private buffers does not by itself prove allocation custody or constant-time execution. The existing independent affine test arithmetic is a test oracle, not a parallel production verifier.

## Vectors and validation

`tests/fixtures/wycheproof_gost.json` contains locally generated deterministic vectors for all five admitted parameter sets: five positive signatures and five modified-signature negatives. The ignored `dump_wycheproof_vectors` helper in `src/signature/gost.rs` records their generation pattern. Its filename and historical labels are not evidence of an upstream Wycheproof import or independent certified GOST vectors. The grouped `gost_wycheproof` test exercises these unchanged bytes through the public API. Independent external signature KATs remain an open qualification gate.

The parameter controls compare all six literal integers and widths, verify generator order against independent affine arithmetic, and exercise full native-width boundaries. Borrowed-verifier controls cover malformed lengths and coordinates, digest byte order/reduction/inversion, scalar bounds, signature/message/key mutations, exact error ordering, cache exclusion, and an explicitly infinite joint relation. The allocator target separately observes compact and owned construction, ordinary/typed/admission/owned verification, and still-allocating malformed diagnostics. A test name or prepared test is not evidence that it ran.

For a coordinated candidate, run the locked Crypto tests and the exact GOST namespace, all public-key allocator tests, GOST-only/no-PQC feature isolation, grouped vectors, codecs, doctests, native consumers and dependency-inclusive strict Clippy. Preserve the existing fixture-generator ignore but require every positive and negative verification control to execute. If source or dependency inputs drift during a build, preserve that run as unqualified engineering evidence and establish a fresh stable candidate before reporting qualification.

## Performance tooling

`benches/gost_sign.rs`, `scripts/gost_bench.sh`, `scripts/update_gost_baseline.sh` and `src/bin/gost_perf_check.rs` own benchmark execution and comparison. The [performance workflow](../../../specs/crypto/gost_performance.md) describes their existing thresholds. Keep checked-in baselines tied to recorded hardware and artifacts; changing a baseline is not a performance pass. Historical medians and finite dudect-style samples do not establish current release readiness, timing resistance or hardware parity.

Non-consensus consumers obtain algorithm permission and authority from normal protocol state. This document makes no new validator-consensus signing claim and does not register State/proof admission or Musubi publication. Public operator guidance belongs in the [Iroha documentation](https://docs.iroha.tech/); this file stays coupled to the implementation and its open validation gates.
