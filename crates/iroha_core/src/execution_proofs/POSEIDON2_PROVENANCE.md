# Execution commitment primitive

Status: implemented for local qualification; **not cryptographically qualified**. This document describes the primitive argument separately from the whole execution proof. It does not authorize a funded profile.

The primitive is one Poseidon2 sponge over the Goldilocks field `p = 2^64 - 2^32 + 1`, with width 16, rate 8, capacity 8, exponent 7, eight full rounds and 22 partial rounds. It emits six canonical field elements. It uses the published initial external matrix, every external/internal round, and the final external rounds. Framed bytes absorb through seven-byte injective field chunks, explicit tags/lengths, per-field delimiters, and final `pad10*` field padding. There is no compression shortcut or independent-lane combiner.

Parameters, internal diagonal and permutation KAT come from [Plonky3 at commit 0df3bdcf5a951a25d03dfba0d7caaf0ebef5622b](https://github.com/Plonky3/Plonky3/blob/0df3bdcf5a951a25d03dfba0d7caaf0ebef5622b/goldilocks/src/poseidon2.rs). Its complete source SHA-256 is `839733ca6956246d57f371af8ed51785e454839a4ccb11c5cad8d6f0d7f664b3`. The native constant file retains the MIT-or-Apache license choice; copies are adjacent. These round constants are the width-16 Grain LFSR instance `(field_type=1, exp_flag=0, n=64, t=16, RF=8, RP=22)`.

The same pinned repository's `poseidon2/generate_constants.py` has SHA-256 `89c51d810f9f79b76ae74128728f9ab8a70f35d13f9c9b947951623928716096`. `sora-cars/scripts/check-poseidon2-provenance.py` checks that source pin, independently regenerates all 150 round constants, and evaluates the complete permutation with the upstream dense Python matrix evaluator. The result matches every word of the published 16-word production KAT. The generator's `--test-vector` option prints embedded literals; it does not compute a fresh permutation. Its optional Grain-generated internal diagonal and default external matrix also differ from the selected Plonky3 production matrices. The check therefore explicitly supplies the published MDSMat4 circulant and structured internal diagonal. `sora-cars/output/qualification/native-proof/poseidon2-v2/provenance-check.json` records the passing comparison, actual native constant-source hash and this matrix distinction.

The [pinned round-number implementation](https://github.com/Plonky3/Plonky3/blob/0df3bdcf5a951a25d03dfba0d7caaf0ebef5622b/poseidon2/src/round_numbers.rs) targets 128 bits, accounting for the statistical, interpolation and algebraic constraints and the additional 2023/537 criterion. The [Poseidon2 design paper](https://eprint.iacr.org/2023/323) supplies the permutation and sponge rationale. The exact mode still requires an independent review of the published analysis and later [subspace-trail cryptanalysis](https://eprint.iacr.org/2025/954); preserving upstream constants and passing a vector are implementation evidence, not a new proof of cryptanalytic resistance.

The generic sponge argument has ample capacity for the requested classical target: `p > 2^63`, so the capacity space `p^8 > 2^504`. The six-output space `p^6 > 2^378` has a conservative generic collision scale above `2^189`. These dimensional margins remove the V1 per-lane-capacity issue, conditional on the published permutation security assumptions. They do not turn the 128-bit permutation target into a 189- or 252-bit cryptanalytic claim. The execution profile target remains 128 bits, and the overall proof still needs complete DEEP/ALI, FRI and Fiat–Shamir analysis.

Legacy Plonky2's original width-12 Poseidon parameters are deliberately not used: [its own security section](https://github.com/0xPolygonZero/plonky2#security) reports a roughly 95-bit estimate for that configuration. The V1 six-lane primitive and all privacy formats remain unchanged in their retained modules.

Validation must include the upstream complete permutation vector, independently regenerated constants, byte-framing boundaries, one-shot/incremental equivalence, exact modulo arithmetic checks and genuine proof roundtrips. CPU scheduling changes and future accelerated backends must produce exactly these permutation/digest bytes. A future GPU/SIMD implementation receives a separate backend evidence manifest and must fail closed or select the same scalar implementation when unsupported; it cannot substitute another sponge or weaken rounds.
