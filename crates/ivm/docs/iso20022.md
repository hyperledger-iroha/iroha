# Iroha 3 IVM ISO 20022 Support: Helper and Reserved Opcode Design

## Introduction and Goals

Hyperledger Iroha 3 is a deterministic blockchain platform with on-chain
permissions and a rich asset/account model. ISO 20022 is a global financial
messaging standard spanning payments, securities, trade services, foreign
exchange, and card transactions. Iroha's current support combines deterministic
schema helpers with Torii bridge endpoints; the related IVM opcode family is
reserved in ABI v1 and is not executable. This design records how that surface
can evolve while preserving Iroha's account, permission, asset, and trigger
semantics. The key goals and constraints are:

Status
- The repository now ships a schema-driven ISO 20022 helper (see `src/iso20022.rs`) whose canonical private table data lives in the versioned `src/assets/iso20022_schema_v1/schema_v1.tsv` asset and is emitted as the same static schemas at build time. It understands canonical field layouts for `pacs.008`, `pacs.009`, `pacs.004`, `pacs.007`, `pacs.002`, `pacs.028`, `pacs.029`, `pain.001`, `pain.002`, `camt.052`, `camt.053`, `camt.054`, and `camt.056` messages. DvP/PvP and collateral substitution flows are fully covered: `sese.023`/`sese.024`/`sese.025` now validate settlement qualifiers (`SttlmParams/HldInd`, `PrtlSttlmInd`, `SttlmTxCond/Cd`), venue MICs, status advice, movement/payment and plan semantics, plus linkage aliases; `colr.012` includes collateral instrument identifiers and haircuts alongside substitution confirmation metadata. Norito schemas live under `ivm::iso20022::norito_schemas::{Sese023,Sese025,Colr012}` and round-trip against fixtures in `fixtures/iso20022/*.xml`; `sese.024` status-advice fixtures pin the canonical parser fields used by Torii lifecycle handling. Each schema encodes mandatory fields, multiplicity, enumerations, and format predicates, and `.001.x` aliases (e.g., `pacs.008.001.10`) resolve automatically to their canonical rule sets.
- `parse_message` can parse and serialize a deterministic internal XML envelope (`<ISO20022 message="…">`) and the former key/value format for developer tooling and tests. Production Torii ingress uses `parse_xml_message`, which accepts only real ISO XML. That parser enforces fixed depth, element, attribute, path, and materialized-field budgets; binds `AppHdr`, `Document`, and all semantic descendants to their exact namespace; rejects conflicting canonical-field aliases while merging the provenance span of byte-identical aliases; and records source-digest/byte-range provenance for every materialized field. XML paths are validated against the loaded schema and values are checked for IBAN, BIC, currency, amount, numeric, date, and enum compliance.
- Checked-in XML fixtures now pin payment status, return, and cancellation lifecycle parsing for `pacs.002`, `pacs.004`, and `camt.056`, alongside the securities and collateral fixtures under `fixtures/iso20022/`.

- Validation helpers continue to expose amount/base64 utilities and the pluggable signing stack (Ed25519, secp256k1, ML‑DSA). The expanded schema adds richer coverage for status codes, account structures, and repeating elements such as `PmtInf[*]/CdtTrfTxInf[*]` or `Stmt/Bal[*]`.
- Key/value parsing remains available for lightweight tests, while helper operations such as clone, add, and remove normalise field names through the same schema layer to guarantee consistent behaviour across formats.
- Torii exposes `/v1/iso20022/pacs008` and `/v1/iso20022/pacs009`, accepting canonical XML envelopes, translating them into on-chain transfer transactions via the configured ISO 20022 bridge signer, and returning the resulting transaction hash once enqueued. A verified XMLDSig reference must cover the provenance of every bridge-consumed field, so a valid inner-subtree signature cannot authorize unsigned header or sibling semantics. Optional supplementary data (`SplmtryData/LedgerId`, `SourceAccountId`, `SourceAccountAddress`, `TargetAccountId`, `TargetAccountAddress`, `AssetDefinitionId`) is validated and captured into transaction metadata for audit trails. Rejected records cannot be revived, and settled payments admit only an explicit `pacs.004` return transition that preserves the original transaction and settlement evidence. `colr.012` records collateral-substitution obligation, original/substitute collateral, effective date, substitution type, haircut, and reason-code context without fabricating ledger instructions.
- Operators can poll `/v1/iso20022/messages/{MsgId}` for lifecycle visibility. Both payment routes reserve the group-header `MsgId` as the primary lifecycle identity; for `pacs.009`, the BAH `BizMsgIdr` remains an independent secondary replay identity and the BAH and group-header creation times remain distinct. The bridge tracks each message (`Pending` → `Accepted`/`Rejected`) and surfaces pacs.002 status codes, transaction hashes, rejection reasons, and the recorded ledger/account/asset hints in deterministic JSON. Admission and secondary replay indexes are updated under one local state lock. The exact signed transaction hash is reserved before queue dispatch; an indeterminate queue-journal outcome remains pinned for hash-based reconciliation instead of reopening the message identity.

## Opcode Set Design for ISO 20022 in IVM

To support ISO 20022 within the Iroha Virtual Machine, we introduce a set of low-level **opcodes** (machine instructions) that extend IVM’s base instruction set. These opcodes are grouped by function for clarity. At a high level, we have:

* **Financial Messaging Opcodes:** Instructions to create, manipulate, parse, and serialize ISO 20022 message structures. These allow the VM to construct messages (or read incoming ones) and access nested fields, effectively mapping message data to Iroha’s internal model.
* **Data Encoding/Decoding Opcodes:** Utility instructions for data format conversions required by financial messages – e.g. translating between IVM internal data types and ISO 20022 field formats (dates, numerical formats, identifiers, etc.). This category also covers generic parsing of structured data (like XML or possibly ASN.1/JSON if needed) at a low level.
* **Permission and Security Opcodes:** Instructions enforcing Iroha’s permission model and other security checks during message processing. These opcodes ensure that any state-changing operations (like posting a payment or security transfer) comply with the role-based access control rules and that message handling can be gated by proper authorizations.

In addition to these new categories, the IVM continues to support standard operations (arithmetic, logic, control flow, and **ledger state opcodes** for asset/account manipulation). Many of Iroha’s native “Special Instructions” (such as asset transfers, account creation, etc.) remain available. The new ISO 20022 opcodes complement these, enabling the VM to bridge between external ISO 20022 messages and internal ledger instructions.

Below, we detail each opcode category with tables and explanations:

### Financial Messaging Opcodes

These opcodes are dedicated to handling ISO 20022 message objects and their content. The IVM treats an ISO message as a structured data object in memory, which can be manipulated via these instructions. The design assumes a **stack-based VM** (like many blockchain VMs), where opcodes pop operands from a stack and push results, although we describe the behavior abstractly. Table 1 lists the key financial messaging opcodes:

**Table 1: Financial Messaging Opcodes**

| **Opcode**             | **Description** |
| ---------------------- | --------------- |
| `MSG_CREATE type`      | Create a new ISO 20022 message object of a given **type** on the stack. The `type` operand might be an identifier (string or enum) like `"pacs.008.001.08"` for a customer credit transfer, or `"camt.053.001.04"` for an account statement. Allocates an internal structure with all defined fields. |
| `MSG_CLONE`            | Copy a message object (e.g. to fork or to create a template). |
| `MSG_SET field`        | Set the value of a specified **field** in the current message object. |
| `MSG_GET field`        | Retrieve a field’s value from a message object. |
| `MSG_ADD field`        | Append a new occurrence of a repeating field/segment. |
| `MSG_REMOVE field`     | Remove a field or substructure from the message. |
| `MSG_CLEAR`            | Clear all fields of the message object (reset to default/empty). |
| `MSG_PARSE format`     | Parse a raw message from a given format into an internal message object. |
| `MSG_SERIALIZE format` | Serialize a message object to a raw format (e.g. XML string). |
| `MSG_VALIDATE`         | Validate the message object against ISO 20022 schema rules and business rules. |
| `MSG_SIGN`             | Apply a digital signature or MAC to the message. |
| `MSG_VERIFY_SIG`       | Verify a digital signature on an incoming message. |
| `MSG_SEND channel`     | Reserved for a future ABI; ABI v1 rejects this opcode and exposes no transport. |

### Data Encoding and Decoding Opcodes

ISO 20022 messages carry a variety of data: numeric amounts, dates, currency codes, identifiers (like IBANs, BICs), code lists, and free-text fields. The IVM provides low-level opcodes to encode or decode these data types to and from internal representations. These **encoding/decoding opcodes** serve two purposes: (1) help parse and format fields when converting ISO messages to internal data, and (2) enforce data format rules (for example, IBAN structure or date format) as part of message validation.
The prototype includes a minimal, constant-time Base64 encoder/decoder with streaming support to allow binary blobs to be attached to messages via `ENCODE_STR`/`DECODE_STR` without pulling in heavy external dependencies.
