# Iroha 3 IVM ISO 20022 Support: Helper Library

## Introduction and Goals

Hyperledger Iroha 3 is a deterministic blockchain platform with on-chain
permissions and a rich asset/account model. ISO 20022 is a global financial
messaging standard spanning payments, securities, trade services, foreign
exchange, and card transactions. Iroha's support combines deterministic
schema helpers with Torii bridge endpoints. The IVM instruction set has no
ISO 20022 opcodes: message handling is host-side library code, and its
results reach the ledger as ordinary transactions. This document describes
that helper surface and how it preserves Iroha's account, permission, asset,
and trigger semantics. The key goals and constraints are:

Status
- The repository now ships a schema-driven ISO 20022 helper (see `src/iso20022.rs`) whose canonical private table data lives in the versioned `src/assets/iso20022_schema_v1/schema_v1.tsv` asset and is emitted as the same static schemas at build time. It understands canonical field layouts for `pacs.008`, `pacs.009`, `pacs.004`, `pacs.007`, `pacs.002`, `pacs.028`, `pacs.029`, `pain.001`, `pain.002`, `camt.052`, `camt.053`, `camt.054`, and `camt.056` messages. DvP/PvP and collateral substitution flows are fully covered: `sese.023`/`sese.024`/`sese.025` now validate settlement qualifiers (`SttlmParams/HldInd`, `PrtlSttlmInd`, `SttlmTxCond/Cd`), venue MICs, status advice, movement/payment and plan semantics, plus linkage aliases; `colr.012` includes collateral instrument identifiers and haircuts alongside substitution confirmation metadata. Norito schemas live under `ivm::iso20022::norito_schemas::{Sese023,Sese025,Colr012}` and round-trip against fixtures in `fixtures/iso20022/*.xml`; `sese.024` status-advice fixtures pin the canonical parser fields used by Torii lifecycle handling. Each schema encodes mandatory fields, multiplicity, enumerations, and format predicates, and `.001.x` aliases (e.g., `pacs.008.001.10`) resolve automatically to their canonical rule sets.
- `parse_message` can parse and serialize a deterministic internal XML envelope (`<ISO20022 message="…">`) and the former key/value format for developer tooling and tests. Production Torii ingress uses `parse_xml_message`, which accepts only real ISO XML. That parser enforces fixed depth, element, attribute, path, and materialized-field budgets; binds `AppHdr`, `Document`, and all semantic descendants to their exact namespace; rejects conflicting canonical-field aliases while merging the provenance span of byte-identical aliases; and records source-digest/byte-range provenance for every materialized field. XML paths are validated against the loaded schema and values are checked for IBAN, BIC, currency, amount, numeric, date, and enum compliance.
- Checked-in XML fixtures now pin payment status, return, and cancellation lifecycle parsing for `pacs.002`, `pacs.004`, and `camt.056`, alongside the securities and collateral fixtures under `fixtures/iso20022/`.
- ABI v1 has no ISO 20022 opcode: every opcode byte outside the 59 admitted instructions is unassigned and rejected as `InvalidOpcode`. The helper functions are library code used by tests and host integrations.
- The IVM helper library performs no network delivery. Host integrations obtain deterministic XML bytes through `msg_serialize` or `parse_message` and hand them to a separately configured, non-consensus transport service.
- Validation helpers continue to expose amount/base64 utilities and the pluggable signing stack (Ed25519, secp256k1, ML‑DSA). The expanded schema adds richer coverage for status codes, account structures, and repeating elements such as `PmtInf[*]/CdtTrfTxInf[*]` or `Stmt/Bal[*]`.
- Key/value parsing remains available for lightweight tests, while helper operations such as clone, add, and remove normalise field names through the same schema layer to guarantee consistent behaviour across formats.
- Torii exposes `/v1/iso20022/pacs008` and `/v1/iso20022/pacs009`, accepting canonical XML envelopes, translating them into on-chain transfer transactions via the configured ISO 20022 bridge signer, and returning the resulting transaction hash once enqueued. A verified XMLDSig reference must cover the provenance of every bridge-consumed field, so a valid inner-subtree signature cannot authorize unsigned header or sibling semantics. Optional supplementary data (`SplmtryData/LedgerId`, `SourceAccountId`, `SourceAccountAddress`, `TargetAccountId`, `TargetAccountAddress`, `AssetDefinitionId`) is validated and captured into transaction metadata for audit trails. Follow-up submission endpoints cover `pacs.002`, `pacs.004`, `camt.056`, `sese.023`, `sese.024`, `sese.025`, and `colr.012`; lifecycle updates must match the original message's profile, business service, and family. Rejected records cannot be revived, and settled payments admit only an explicit `pacs.004` return transition that preserves the original transaction and settlement evidence. `colr.012` records collateral-substitution obligation, original/substitute collateral, effective date, substitution type, haircut, and reason-code context without fabricating ledger instructions.
- Operators can poll `/v1/iso20022/messages/{MsgId}` for lifecycle visibility. Both payment routes reserve the group-header `MsgId` as the primary lifecycle identity; for `pacs.009`, the BAH `BizMsgIdr` remains an independent secondary replay identity and the BAH and group-header creation times remain distinct. The bridge tracks each message (`Pending` → `Accepted`/`Rejected`) and surfaces pacs.002 status codes, transaction hashes, rejection reasons, and the recorded ledger/account/asset hints in deterministic JSON. Admission and secondary replay indexes are updated under one local state lock. The exact signed transaction hash is reserved before queue dispatch; an indeterminate queue-journal outcome remains pinned for hash-based reconciliation instead of reopening the message identity.

* **ISO 20022 Structure & Semantics:** Support all message categories (payments, securities, trade, FX, cards) by providing helper functions to represent, parse, and construct ISO 20022 messages so host integrations can map their contents to on-ledger actions.

It parses, validates, signs, and serializes messages but has no transport side effects; network delivery belongs outside the IVM and outside consensus execution. Validation spans IBAN/BIC checks (country-specific lengths plus ISO 7064 mod-97), currency codes, numeric amounts (with precision limits), ISO dates/timestamps, and constrained enumerations for fields such as `TxSts`, balance codes, and charge bearers. Signing helpers and base64/amount utilities remain available to host integrations.

## Helper Functions for ISO 20022

The helper library in `src/iso20022.rs` is host-side Rust code, grouped by purpose for clarity. At a high level, we have:

* **Message Helpers:** Functions to create, manipulate, parse, validate, and serialize ISO 20022 message structures. These allow a host integration to construct messages (or read incoming ones) and access nested fields, effectively mapping message data to Iroha’s internal model.
* **Data Encoding and Validation Helpers:** Utility functions for the data formats required by financial messages (identifiers, currency codes, amounts, dates, and base64 payloads).

The helpers perform no ledger operation. Iroha’s native “Special Instructions” (such as asset transfers, account creation, etc.) are submitted as ordinary transactions by the integration that consumes a validated message.

Below, we detail each category:

### Message Helpers

These functions handle ISO 20022 message objects and their content. They operate on a thread-local stack of messages: the most recently created or parsed message is the current one. Table 1 lists them:

**Table 1: Message Helpers**

| **Function**            | **Description** |
| ----------------------- | --------------- |
| `msg_create(type)`      | Push a new, empty ISO 20022 message of a given **type**, such as `"pacs.008"` for a customer credit transfer or `"camt.053"` for an account statement. It becomes the current message. |
| `msg_set(field, value)` | Set the value of a specified **field** in the current message. |
| `msg_get(field)`        | Retrieve a field’s value from the current message. |
| `msg_add(field)`        | Append a new, empty occurrence of a repeating field/segment. |
| `msg_remove(field)`     | Remove a field or substructure from the current message. |
| `msg_clear()`           | Clear all fields of the current message. |
| `msg_parse(type, data)` | Parse a raw message (the internal `<ISO20022>` XML envelope, real ISO 20022 XML, or the key/value test format) into a new current message. |
| `msg_serialize(format)` | Serialize the current message as `XML` or as key/value text. |
| `msg_validate()`        | Validate the current message against its ISO 20022 schema rules; `take_validation_error` returns the recorded failure. |

`parse_message` and `parse_xml_message` wrap parsing and validation and return an owned `ParsedMessage`, removing the temporary stack entry.

### Data Encoding and Validation Helpers

ISO 20022 messages carry a variety of data: numeric amounts, dates, currency codes, identifiers (like IBANs, BICs), code lists, and free-text fields. The validation helpers enforce data format rules (for example, IBAN structure or date format) as part of message validation; `validate_identifier` exposes the ISIN, CUSIP, LEI, BIC, MIC, IBAN, and currency-code checks directly.
The library includes a minimal Base64 encoder/decoder (`encode_base64`, `decode_base64`, `decode_base64_into`) using constant-time table lookups, so binary blobs can be attached to messages without pulling in heavy external dependencies.

### Permissions and Ledger Operations

Because Iroha authorizes every state change, any operation triggered by an ISO 20022 message must obey the platform’s access control rules and preserve security invariants. The helper library holds no authority of its own: ledger updates derived from a message are ordinary signed transactions, authorized by the executor like any other.

## ISO 20022 Message Representation in IVM

The helper maintains an internal **schema-driven object model** for ISO 20022 messages. Each message is a flat map from canonical field names to encoded values, with indexed keys for repeating elements, kept on a thread-local stack. A message parsed from real ISO XML also records the digest of its source and the byte range that owns each materialised field.
