## Original attack path (before the cutover)

Before this cutover, governance could bootstrap an Orchard pool with an existing public `reserve_account`, asset definition, and balance scope. The bootstrap checked the account and pool namespace, but did not make the reserve a protocol-owned debit source or reject another pool using the same exact reserve balance. Private-IVM proof-managed bootstrap likewise checked its required reserve account but did not install debit custody. See [`privacy.rs` Orchard bootstrap](../../../crates/iroha_core/src/smartcontracts/isi/privacy.rs), [`privacy.rs` proof-managed bootstrap](../../../crates/iroha_core/src/smartcontracts/isi/privacy.rs), and the [typed pool bootstrap fields](../../../crates/iroha_data_model/src/privacy/protocol.rs).

An accepted directional Orchard or private-IVM proof moves transparent value through `execute_verified_privacy_public_balance_transfer`: deposits move the submitter's asset into the reserve, withdrawals move the reserve's asset to the submitter. The same helper also serves ZK-ACE authorized public transfers. Its retained `PrivacyPublicBridge` purpose currently maps to the ordinary `User` source policy. See [`privacy.rs` effect application](../../../crates/iroha_core/src/smartcontracts/isi/privacy.rs), [private-IVM effect application](../../../crates/iroha_core/src/smartcontracts/isi/privacy.rs), [ZK-ACE effect application](../../../crates/iroha_core/src/smartcontracts/isi/privacy.rs), and [`asset.rs` purpose mapping](../../../crates/iroha_core/src/smartcontracts/isi/asset.rs).

The reserve is also an ordinary `AccountId`. A holder of its signing authority, `CanTransferAsset`, or `CanTransferAssetWithDefinition` can submit an ordinary transfer from that account. Core checks the user/permission source authority, but the numeric movement policies have no privacy-reserve source check; they return early for some protocol custody policies. This can remove transparent collateral while private notes remain outstanding. See [executor transfer authorization](../../../crates/iroha_executor/src/default/mod.rs), [Core source authority](../../../crates/iroha_core/src/smartcontracts/isi/asset.rs), and [Core policy gate](../../../crates/iroha_core/src/smartcontracts/isi/asset.rs).

An ordinary burn is another debit route. The executor allows the reserve account owner, the asset-definition owner, `CanBurnAsset`, or `CanBurnAssetWithDefinition`; Core's burn handler has no privacy-reserve check before `withdraw_numeric_asset`. Account-level outgoing transfer controls therefore do not protect against this burn. See [executor burn authorization](../../../crates/iroha_executor/src/default/mod.rs) and [Core burn](../../../crates/iroha_core/src/smartcontracts/isi/asset.rs).

A multisig reserve account can be rekeyed: `rekey_account_id` directly removes each old asset ID and reinserts it under the replacement account before any privacy-pool binding changes. This strands the governed reserve even if transfer and burn are blocked. See [rekey preflight and asset move](../../../crates/iroha_core/src/smartcontracts/isi/multisig.rs). Existing account, asset-definition, and domain unregistration checks retain Orchard dependencies, but the corresponding private-IVM reserve/configuration is not covered. See [`domain.rs` account and definition guards](../../../crates/iroha_core/src/smartcontracts/isi/domain.rs) and [domain removal guard](../../../crates/iroha_core/src/smartcontracts/isi/world.rs).

## Implemented first-release cutover

1. The existing authoritative `privacy_commitments` map now carries a closed `PublicReserveCustody` key and record. The key uses protocol plus a domain-separated digest of the canonical scoped `AssetId`; the record retains the **full `AssetId`**, pool namespace, and bootstrap digest. Direct lookup probes the two permitted protocols and refuses a digest/full-ID mismatch or double claim. See [privacy_state.rs](../../../crates/iroha_core/src/privacy_state.rs).
2. Orchard and private-IVM bootstraps insert that row atomically with the governed pool state. Restore derives the exact required set from those pool records, rejects missing/extra/malformed custody, and checks the reserve account and asset definition before constructing the world. Reserve-free FCMP++ and PQ-MASP pools remain valid. See [privacy.rs](../../../crates/iroha_core/src/smartcontracts/isi/privacy.rs) and [deserialize_world.rs](../../../crates/iroha_core/src/state/deserialize_world.rs).
3. The numeric transfer path checks the resolved source before implicit recipient admission and again before protocol-custody early return. Ordinary owner/permission transfers, independent batch legs, and the generic ZK-ACE bridge cannot debit a pool reserve. Only the separately typed Orchard/private-IVM post-verification bridge with the exact owner, direction, statement, asset, scope, parties, and quantity can release it. See [asset.rs](../../../crates/iroha_core/src/smartcontracts/isi/asset.rs).
4. The shared withdrawal path denies reserve burns. Multisig rekey and account, definition, and domain removal preflight the typed custody inventory before relocating or deleting assets. See [multisig.rs](../../../crates/iroha_core/src/smartcontracts/isi/multisig.rs), [domain.rs](../../../crates/iroha_core/src/smartcontracts/isi/domain.rs), and [world.rs](../../../crates/iroha_core/src/smartcontracts/isi/world.rs).

## Focused validation and remaining limits

- [Privacy state tests](../../../crates/iroha_core/src/privacy_state.rs) cover full-ID mismatch, cross-protocol double claim, missing/extra restore rows, private-IVM restore, and a reserve-free PQ-MASP restore. [Asset tests](../../../crates/iroha_core/src/smartcontracts/isi/asset/privacy_public_reserve_tests.rs) cover owner/delegate/general-bridge/burn denial, forged owner/direction, exact pool-bridge debit, implicit-recipient non-creation, and independent-batch sibling application. [Multisig tests](../../../crates/iroha_core/src/smartcontracts/isi/multisig.rs) preserve the old account and asset on rekey refusal; [snapshot tests](../../../crates/iroha_core/src/state/tests.rs) exercise restored dependencies.
- The three production calls to low-level `apply_prechecked_numeric_asset_transfer_delta_exact` consume non-serialized, one-shot plans prepared under the source-policy guard in the same instruction. The prepared numeric plan now retains its original typed source policy, and the low-level mutator rechecks current governed custody against that policy before changing either balance. The separately prepared SCCP inbound release supplies its exact SCCP source policy. Two owner-bound tests stage a new reserve claim between preparation and ordinary/batch application and require both balances to remain untouched. This does not make a future durable prepared-plan layout admissible without its own authenticated source-policy binding and recovery proof.
- The per-transfer exact-ID digest now streams the complete canonical Norito frame into its BLAKE3 key, removing the separate output-sized ID buffer. A byte-identity test compares both protocol keys to the original framed-preimage formula for two distinct account IDs; a second test verifies the key ignores ambient noncanonical Norito layout flags. Serializer-internal scratch, lookup/error allocation, and the broader resource-admission gate still require accounting. Duplicate governed-bootstrap paths, every burn authority variant, transaction rollback/replay under four validators, full cryptographic conservation, and proof qualification require further adversarial and deployment evidence.
- The repository-wide `scripts/check_source_file_budget.py` still reports 234 findings across the combined checkout, including other changed Core files; the global gate is open. This cutover moved its asset tests below the 3,000-line cap and extracted shared privacy fixtures, lowering `privacy_state.rs` from 15,783 to 14,331 lines and ratcheting only its exception baseline to 14,331.

This custody guard closes a transparent collateral-drain route. Full confidential-asset conservation still depends on the separately gated cryptographic relations and their independent review.
