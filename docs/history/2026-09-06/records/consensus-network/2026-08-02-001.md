## 2026-08-02 Sumeragi v2 revision-4 source implementation



<a id="record-65aeb0cbf999e1710cd8d2e65ac5ace8c00d9a7be2763a43c44dc49944575e3e"></a>

- The data-model wire and pure reducer context now identify protocol revision
  4. Height, genesis, next-epoch, status, and configuration validation admit
  only exact `3f + 1` committees from 4 through 31 validators (`1 <= f <= 10`)
  and assign every committee member equal unit voting weight in both
  permissioned and NPoS modes.


<a id="record-56418dec1c80f26fe1db8c48c2298b657d0837a0941b6e4b68e7390d0dfb5dc3"></a>

- Frozen height contexts require a non-empty Reed-Solomon-16 data-availability
  layout and reject resource geometry above 16 data shards, 16 parity shards,
  32 total shards, 256 KiB chunks, a 16 MiB payload, or 1,024 encoded chunks.
  Parity expansion and pre-manifest orphan acquisition are capped at 32 MiB.
  Authenticated partial shards stay in bounded memory and are reacquired after
  restart, avoiding per-shard durability barriers. Prepare remains gated on
  complete canonical-body reconstruction, one durable canonical-body write,
  hash verification, and deterministic validation.


<a id="record-5af255d1a3152b65ed9d8b0fdebd051dc7b3fa79ef6919445eccc791bbaaf019"></a>

- The 3,600-height NPoS epoch is exactly a 3,600-non-empty-finalized-block
  epoch because empty blocks fail deterministic validation before they can
  receive Prepare/Commit votes. Terminal contexts retain the old-roster
  authenticated next-epoch roster, PoPs, seed, and equal-vote quorum.


<a id="record-ae423f132527799359d473ed230342bc1d744ce59cbe96e54a03d7c8af2015c3"></a>

- The pure committee projection assigns stable roster indices, quorum
  `2f + 1`, a cyclic height/view order, Set A, Set B, leader, and proxy tail.
  Production routing sends proposal manifests committee-wide, first-send body
  chunks to Set A, votes directly to the proxy tail, and retry/recovery traffic
  committee-wide.


<a id="record-ecff3dc27e07b97c86adaaa03ee97411d105b87fde323b284e3ab9e5a53aadd1"></a>

- Fresh-network construction in Swarm, Kagami, xtask profiles, and Mochi
  rejects every roster except 4, 7, ..., 31 validators. Generated development
  and SDK integration profiles start all four default validators instead of
  relying on unauthenticated block sync to create genesis state.


<a id="record-680b87ab23b48338d7aad0f8ffd392d66f2b4ca2189beba674cd24f2c60ef607"></a>

- Genesis signing accepts an explicit creation-time base and assigns checked,
  deterministic transaction and block timestamps. Deployable static profile
  runs generate one exact bound manifest plus canonical signed wire shared by
  every peer. The checked-in public Nexus sample remains an inert unsigned
  template until an operator supplies its canonical XOR asset-definition ID.
  Swarm Compose is validator-only: every service consumes one owner-prepared
  canonical signed body plus independently provisioned canonical verifier-key
  and expected-hash records. Prepared mode derives every runtime identity from
  the validated `peerN.toml` bundle, derives a content-addressed container-safe
  projection without ambient environment overrides or `extends`, and proves
  that its Sumeragi, deterministic execution, and Nexus/AMX fingerprints match
  the admitted source. Each owner-held projected TOML is bound to the daemon by
  an exact BLAKE3 command-line digest and an empty launch environment. Public
  binary runtime inputs are hash-interned as base64 Compose configs and decoded
  into protected per-service files; account-onboarding and faucet private keys
  use dedicated file-backed Compose secrets and never appear in YAML content or
  environment variables. Validator private keys remain only inside the
  owner-held projected config secret; the original source configs and genesis
  signing material are not mounted.
  Every path redirected to a named per-validator storage volume is admitted
  only when its effective source file or directory is absent or empty,
  including omitted/default paths and PoW, PoP, moderation, evidence, gateway,
  privacy, ISO, and Governance DAG state. Unsupported relay, proxy, TLS, SCION,
  tunnel, background-prover, push, bridge-trust-CIDR, and helper-service
  topologies fail closed; loopback-only Torii source CIDRs remain local to the
  container.
  Deterministic development mode requires the same three artifact paths at
  Compose evaluation. Neither mode mounts a genesis private key or source
  manifest or runs a signer in the validator graph. Kagami localnet emits and
  cross-checks the complete bundle, while
  xtask profiles now keep staging relative to the bundle root and emit the
  same public key, expected hash, and prepared peer-config names. Prepared
  admission also re-encodes the signed wire canonically and proves that its
  instruction batches exactly realize the supplied bound manifest, including
  the staging-derived consensus commitment.


<a id="record-c5cb0037e9e3f70ca4cd9290c5c844a51e096136ce1f54564fd3f85cf90c5a9c"></a>

- The Taira profile now matches the protocol's 16 MiB DA ceiling and uses the
  corresponding 34 MiB per-source ingress budget. The four-validator operator
  template retains a 204 MiB aggregate floor, while the generated
  seven-validator Kagami profile allocates all nine authenticated source
  partitions (306 MiB). One maximum 10 MiB transaction
  with a 9 MiB privacy action fits while smaller transactions may share the
  remaining body capacity.


<a id="record-3108670d1febc96a3df139a4da7606604e719b54aa0f8959fb45d945a32bd9a2"></a>

- Durable application now releases successor construction through one
  serialized, move-only output handoff. The predecessor retries responsive
  targets, verifies Kura/finality reconstruction for every remaining fanout,
  seals its exact-output corridor, and transfers the sole merge-sidecar journal
  owner to the successor. There is no bounded worker pool that can drop a fifth
  output and no old/new journal dual-writer interval.


<a id="record-17b94bcc6991e76c7376dfca69e7a8201acca60e7d2f58273a8de6be392a3cab"></a>

- The successor merge-sidecar responder reserves the complete live roster plus
  one full 31-validator predecessor committee. Removed requesters must belong
  to Kura's exact durable immediate-predecessor roster before allocation and
  prove the exact finalized carrier before response materialization; arbitrary
  older identities cannot occupy that rollover corridor or consume a
  live-roster slot. A predecessor member may still request an older carrier
  for which its frozen carrier context grants authority. Stale generations and
  duplicate/rate admission run before carrier/archive lookup; the durable
  requester-fair scheduler performs expensive immutable Kura authentication
  only for the occurrence selected to materialize. Same-roster durable V3
  lifecycle journals monotonically expand from the former `N`-stream geometry
  to `N + 31` without resetting generation or responder ownership; shrinks
  remain rejected. Kura's version-3 retained block record captures the exact
  compact merge reference while the canonical body is present, so a holder can
  serve an authenticated predecessor after remote-only body eviction;
  recipients still verify the reference and merge QC against their own
  carrier. Canonical version-2 records remain restart-readable, and an exact
  available body is atomically promoted to version 3 by the mandatory
  pre-eviction persistence path; a remote-only legacy record never synthesizes
  missing authority. The joint retained-record byte ceiling now explicitly
  covers the complete legacy SCCP envelope, the independently bounded merge
  reference, and Norito envelope framing.


<a id="record-d46de5233c95eec265475fd764fae836cb27be474a514a93067a7ee4fd7af886"></a>

- Current-height lane Prepare, Commit, QC, certificate, and NewView progress is
  gated on the exact global Decision, not merely on a PrepareQC lock.
  Predicate-aware cache drains retain inadmissible evidence instead of
  consuming it, so a direct cache insertion cannot bypass that gate or strand a
  later valid retry.


<a id="record-5207aecae4022c121010f5e67a402498db6e0bbaeb1e66124d2abd60c51ceaee"></a>

- Unfinished lane state remains owned by the finalized predecessor; it is not
  moved into the successor. The active lifecycle rehydrates late canonical
  bodies, services bounded historical recovery, and withholds rollover
  authority until every winning lane certificate and ordinary application
  receipt or autonomous durable record is independently readable from Kura. A
  configured validator removed from the successor roster has no successor
  global vote, but still performs lane work whenever an exact older or
  independently pinned current-height lane descriptor names it; current Nexus
  lane committees need not be successor-roster subsets. Proof-carrying
  historical output is retired only after exact Kura-backed certificate and
  application evidence is revalidated.


<a id="record-f38681d2a36aa779414bfd4c21e41bed227c49e26e75fc0896f18756508efc56"></a>

- Post-finality body retirement and directory cleanup are handed off
  non-blockingly to one bounded runner-lifetime janitor. A full or disconnected
  cleanup queue retains the files and emits an operator warning; consensus
  never joins a live context worker or performs recursive cleanup on the height
  transition.


<a id="record-5f200f188f3bb117f368cc6e24c8cded10e4a55696bc7601387fee97e88ac8bb"></a>

- The authoritative revision-4 specification and compact TLA+ model record the
  bounded committee, fast/fallback/view-change, mandatory full-body, safety,
  and nonblocking-successor contracts. Older revision-3 formal material and V1
  operator text are marked historical.
