## 2026-09-02 Native Torii MCP protocol and capability hardening



<a id="record-4f913f6b6a4b9d30f16c4e6a09de7a1fbcdd35c00bea46e944448e6f6d6e6751"></a>

- Torii remains the only MCP server, process, and listener on its existing
  `POST /v1/mcp` route. Route-backed tool and resource dispatch re-enters the
  authoritative Torii router in-process, while explicit Torii-local helpers run
  inside the same MCP handler without a fabricated route. No gateway, sidecar,
  proxy server, second listener, or separate MCP deployment unit was added or
  planned.


<a id="record-743d9c696554d42a5b4e924aeb866e833fe50fd335d3a121130caaa37d6ec706"></a>

- The primary transport implements stateless MCP `2026-07-28` with required
  per-request protocol metadata, exact mirrored method/name headers, canonical
  Base64 sentinel encoding for header-unsafe names and URIs,
  `server/discover`, strict modern request identifiers, typed header/version
  failures, request-scoped extension negotiation, self-describing results, and
  private cache hints. Initialization-based `2025-06-18` remains isolated as a
  compatibility adapter on the same Torii route.


<a id="record-c2da76f8cae064efaf69debe96ad6b27bf6744c2562d67c9e8178267a3d2f346"></a>

- Tool descriptors now publish orthogonal operation, authority, mutation,
  retry, world-boundary, sensitivity, and external-signature semantics.
  Standard MCP annotations derive from those dimensions. Route-catalog
  admission remains authoritative and fail-closed for route-backed tools;
  explicit in-process capabilities retain their registered backing and handler
  policy without fabricated route-auth metadata.


<a id="record-f6e6e6c2941bd1be4adc5ca5e1390edde061a4d9453ee0e68094094f228de6da"></a>

- Torii-local operator projection retains its profile-plus-exposure double
  opt-in. Configuration now rejects `expose_operator_routes = true` unless the
  selected profile is exactly `operator`; no separate operator MCP process or
  listener is introduced.


<a id="record-50bd32d69e96f89ac2ac6a2bad51bbe0aa140818cbeb586e2afd65358cb9a45f"></a>

- Native `resources/list` and `resources/read` expose only a fixed reviewed set
  of Torii reads for health, API version, chain head, optional chain parameters,
  and runtime ABI hash. Resource reads share Torii's existing admission,
  response bounds, and MCP dispatch capacity rather than creating another
  network hop.


<a id="record-27822e7e76c2f3b3374725ed15b35a01f0d503b4a72e7e9a1549ed888d3ef6c0"></a>

- `iroha.transactions.prepare` and `iroha.transactions.inspect` are explicit
  in-process capabilities rather than fabricated HTTP routes. They validate
  canonical unsigned payload or fixed-V1 signed-wire archives against Torii's
  exact network id, return bounded content-minimizing summaries and external-
  signing material, and verify complete signed envelopes without accepting a
  private key, mutating state, dispatching a route, or claiming state-aware
  simulation. The signed artifact remains externally assembled and is
  submitted through the existing transaction tool.


<a id="record-39be0a024284aea4b858c9b8dc8a379e3a7ed31066357bb00fa2d42b0660a2a8"></a>

- Mochi, Taira doctor/devnet, edge CORS configuration, and Codex plugin guidance
  use the native stateless request contract. Focused Python validation passes
  the 155-case Taira devnet suite and 19 edge-renderer tests; targeted Rust
  formatting and whitespace checks pass. Focused Rust compilation remains
  unqualified because the current checkout stops in unrelated `iroha_core`
  `StateTransaction: WorldReadOnly` errors. No `Cargo.lock` change is part of
  this work.
