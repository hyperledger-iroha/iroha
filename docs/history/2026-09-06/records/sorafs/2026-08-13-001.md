## 2026-08-13 SoraFS orderbook signed-submit SDK hard cut



<a id="record-ec91ffd4017fdaf508cd0357fad16237b4cc010cfd159094ddfdc753f1c4ab8e"></a>

- This entry supersedes the historical 2026-06-24 orderbook-submit transport
  description. JavaScript and Python now accept an already-signed canonical
  versioned transaction, validate its pinned network, authority signature,
  singleton route instruction, embedded payload signature, and locally
  knowable order/cancel authority before opening HTTP. They derive the three
  authoritative (currently equal) transaction identities locally and send the
  exact inspected byte snapshot; no request-envelope signing or JSON response
  normalization remains on this boundary.


<a id="record-d5da4e2068852dab70be061014e01da8d5e24c2fd7d984a992bc8af76ea68aa1"></a>

- Each submit requires an exact expected Torii receipt public key and a strict
  native inspector/verifier. The standalone Python client accepts an injected
  provider and otherwise fails before HTTP; `iroha_python` supplies its native
  adapter. An accepted response must be exactly `202`, unencoded bounded
  Norito, carry all three independently checked raw lowercase identity
  headers, and contain a canonical signature-verified receipt bound to the
  pinned signer and identities.


<a id="record-d60a672cded45845fd479490ee44636735891c91043d1b7067640ef01114632a"></a>

- Once dispatch starts, transport, status, header, body, or receipt failure is
  reported as a payload-free ambiguous-admission error with explicit
  reconcile/do-not-resubmit guidance. Focused JavaScript and pure-Python tests
  cover preflight zero-send failures, mutable-input snapshots, fixed headers,
  one-shot dispatch, bounded streaming, exact receipt output, and ambiguous
  post-dispatch failures; ABI-22 artifact gates require both new native exports.
