## 2026-08-26 first-release merge reconciliation and public Taira boundary



<a id="record-1566ef0615b7bab16ea2a080f7d75a4f8c79ae15c471b9420d2b952696d88079"></a>

- The merged first-release surface keeps uploaded models as registry/storage
  records only. Private execution, key-release, model-host scheduling, generated
  Hugging Face runtime placement, and compatibility adapters remain deleted;
  future execution must enter through a new signed and pinned Inrou guest.


<a id="record-dfe9aeafe0690e011d9bb8ceb63e732135963cbe961971e4cd7849c5909dd774"></a>

- Taira is the persistent public testnet, not a disposable cohort. The local
  four-validator harness remains a mandatory full guest-workload qualification
  tool and is explicitly separate from public node onboarding. The intended
  public join contract is one signed, versioned bootstrap bundle plus locally
  generated keys through one permissionless-observer `iroha taira join` flow.
  Validator activation follows the existing on-chain staking and peer lifecycle
  rather than an undefined operator admission token. The command and bundle are
  tracked as outstanding work and are not presented as already shipped.
  The misleading generic Kagami Taira wizard path is removed while canonical
  Taira genesis, release, diagnostic, and durable public-reset tooling remains.


<a id="record-ae77b38c73e08e85cd13cbc0555d26fe62ec58ec3d9f69e3846afc3abefcbfdb"></a>

- The five release OpenAPI files retain one byte-consistent inherited unsigned
  bundle from the pre-reconciliation source commit. The package-local source
  mirror reflects the reconciled router, but release provenance cannot be
  regenerated honestly until the source and lockfile are recorded in a clean
  signed commit. The release generator and alias synchronizer must then be
  replayed from that commit; no dirty-worktree manifest is treated as release evidence.

## 2026-08-26 Taira prepared-mutation hard-cut audit



<a id="record-f16bce81d44ee702bc8a050b033d3ff66380797aaca4f75d53f54e8bd82350ff"></a>

- The first-release public-reset mutation closure is seven ordered children, not a
  one-shot canary: `onboarding` -> `faucet` -> `write_canary`
  (`final-canary`), followed by `inrou_bundle_pin` (`bundle-pin`) ->
  `inrou_guest_pin` (`guest-pin`) -> `inrou_discovery_pin`
  (`discovery-pin`) -> `inrou_canary` (`service-mutation`). Each child owns one
  canonical authorization-, phase-, and idempotency-bound envelope. The
  root-custodied host coordinator must publish the exact envelope first-wins
  before one submit; response loss may invoke only read-only recovery of those
  retained bytes. Every later child requires exact Applied evidence for its
  predecessor.


<a id="record-94491104b6253115f90aeaadc8bfa4af72b8fe5a615d8f0cca4a45dece7b288c"></a>

- The hard cut is implemented. Reset inventory pins the complete signed
  onboarding request. The root-custodied host authenticates the exact retained
  receipt, result, request binding, network, and complete request rather than a
  semantic-hash echo. `ProofRequired` is nonterminal, carries no transaction,
  and is never submitted. Every prepare or reopen, including recovery through
  an already-Applied successor, re-proves its onboarding predecessor with one
  redirect- and retry-disabled `POST /v1/accounts/onboarding/current-state`.
  Torii answers from one committed `StateQueryView` with the exact network,
  account, alias, account-existence bit, required nullable alias target,
  nonzero block height, and typed block hash. No split account/alias/status
  observation path remains.


<a id="record-7833f48f60fefc16aa929355c22f317e7ec45e4e17b47da587523e4e47021425"></a>

- Durable coordinator recovery now persists the exact successor phase for both
  ordinary and Applied outcomes. Recovery no longer accepts a predecessor-phase
  compatibility form, closing the crash window without adding a second journal
  interpretation.


<a id="record-8b8f49ba46b745c1538fd8235694a53a3b667cbebec9142209b3bdf8ac126c6b"></a>

- Focused evidence is green at this checkpoint: CLI `proof_required_` 6/6
  (including forged signature, request substitution, missing account,
  conflicting alias, expiry recovery, and split-height rejection), durable
  successor recovery 3/3, and exact reset inventory 1/1; Torii exact-request
  2/2, expired no-dispatch 1/1, and MCP flat/dual-shape rejection 1/1; Kotlin
  golden plus two HTTP regressions; Java golden, alias, and Java-8 regressions;
  and descriptor checks 3/3. The retired-codec guard and stale SDK surface scans
  are clean. Release-wide workspace tests, strict all-target Clippy, and the
  physical corridor remain outstanding.
