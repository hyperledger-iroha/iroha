## 2026-05-26 SCCP Solana account-opening hash binding



<a id="record-8dd81a7d4004556cbe1d4ccdf2d5a7beddcd0afe1bdf658540d1a952f58eebd8"></a>

- Bound Solana validator vote/stake account state hashes to canonical
  `sccp:solana:account-opening:v1` openings. Each opening now commits to the
  account address, owner program id, lamports, rent epoch, executable flag, and
  account-data hash.


<a id="record-cf70a8ef41275e1ef000dd35128b644cc55278803e589f73f59019922795e23a"></a>

- The Rust Solana finalized-vote verifier now requires one vote-account opening
  and one stake-account opening per validator, checks the opening address
  against the account address in the finality context, requires Vote-program
  ownership for vote accounts and Stake-program ownership for stake accounts,
  rejects executable accounts, and compares the supplied account hash to the
  derived opening hash.


<a id="record-5c218dbbbd6503b86dd217042e0ad042a31ab4ac06b23374ede10ef8f6a28714"></a>

- JavaScript, Python, Swift, Kotlin, and Java Android SDKs now expose matching
  account-opening canonical-byte/hash helpers so web and mobile UI provers can
  derive the same account hashes before submitting source proofs on-chain.


<a id="record-f6223403dc6f62a4b6ab5e05c6ae9abf83032b8b4522af987daebe7fb673eb90"></a>

- Updated bridge-proof docs and roadmap text. The remaining Solana production
  work is authenticated account/sysvar inclusion proofs, raw vote/stake/sysvar
  witness binding, full Tower vote-account/state replay, bank
  execution/fork-choice checks, recursive verifier deployment, and live
  submission validation.
