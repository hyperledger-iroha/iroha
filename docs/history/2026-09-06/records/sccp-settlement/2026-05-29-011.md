## 2026-05-29 SCCP EVM destination bytecode replay gate



<a id="record-d96e6d91e714f4e2076e447e6f6e6e6d29810fb8de29f491b6fe7e0756b315ad"></a>

- Hardened the reference-only EVM secp256k1 verifier so it now rejects
  non-canonical attestation ABI length/offsets, including decodable but shifted
  dynamic signature tails, zero native-proof hashes, zero SCCP
  statement/public-input fields, mismatched message/commitment public inputs,
  zero target domains, target-domain overflow, and same-source/target
  attestations before signature recovery. This keeps the non-production
  attestation path aligned with Rust envelope canonicality checks while
  production remains gated on Groth16 deployment evidence.


<a id="record-d6aa54f2c68e047298176f0291059780ddcd4f0d46aa75e0b4386cd152bd6d52"></a>

- Hardened ETH/BSC destination rollout evidence so live TOML carries the
  bridge wrapper and verifier `eth_getCode` runtime bytecode alongside their
  runtime code hashes. Direct EVM destination TOML now requires replayable
  bridge and verifier runtime bytecode too, and JSON summaries keep
  `toml_ready = false` until both bytecode blobs hash back to the advertised
  code hashes.


<a id="record-01a5c1ce93646151670da12fdd88af8eaa09b5242c6fca4c39a319d2964affa5"></a>

- The all-lanes preflight now requires `sccp_evm_bridge_runtime_bytecode_hex`
  and `sccp_evm_verifier_runtime_bytecode_hex` for ETH/BSC destination rollout
  records, decodes them, recomputes Keccak-256, and rejects staged evidence
  whose replayed hashes drift from the live code-hash metadata or structured
  `verifier_code_hash`.


<a id="record-7888af052d7205992773d27a10b2cc87e48438e3a9a50739ed1e24c759301e1e"></a>

- Direct/live ETH/BSC TOML also carries canonical
  `evm-groth16-bn254-v1` verifier-backend and `stark-fri-v1` proof-family hash
  comments. The all-lanes preflight rejects missing or drifting backend/family
  metadata before route activation.
