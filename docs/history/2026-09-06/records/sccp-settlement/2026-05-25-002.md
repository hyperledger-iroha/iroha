## 2026-05-25 SCCP TRON receipt-log source policy binding



<a id="record-709070b2e92ed5b05c9bd3b2d8d3c2b9558d074345bd6daf17b1da9114b9240a"></a>

- Added an explicit `sccp:tron:event-log-source-policy:v1` marker to the TRON
  source verifier material transcript so deployed TRON source material commits
  to the receipt-log `TransactionInfo` source path and cannot be reused as if it
  covered TVM account/storage state proofs.


<a id="record-0d3369eb6b620b757a154962a0214546b4b41bd1206696fba5d74fc4c3d868aa"></a>

- Updated the TRON readiness blocker, bridge-proof docs, and roadmap to reflect
  that current TRON `accountStateRoot` is header-authenticated but not an
  Ethereum-style contract `storageRoot`/`codeHash` commitment. State-derived
  TRON claims remain unsupported until a future consensus-authenticated
  contract-state root and distinct source proof plan are available.


<a id="record-bada0655f113f2b8f20ff2ef6560fcf762aeff28628445e56c603b3b531605cf"></a>

- While validating the full SCCP suite, tightened the Solana stake transcript
  boundary rule so validators activated at the signed epoch are rejected
  (`activation_epoch < epoch`) across stake-activation, stake-account-state,
  and StakeHistory hashing. A later warmup/cooldown replay slice allows
  cooling-down stake when the replay still yields effective voting stake.
