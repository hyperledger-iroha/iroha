## 2026-07-11 SCCP exact first-release implementation (validation in progress)



<a id="record-04fce46beef06490bf91b3ab1e9cebf01d283fef987be2b578c91e815d1b8a94"></a>

- The authoritative first-release scope is SORA Taira paired with Ethereum
  mainnet, BNB Smart Chain mainnet, and TRON mainnet. Solana, TON, generic
  proof jobs/artifacts, compatibility manifests, and Nexus settlement are not
  SCCP V1 launch surfaces. Every value-moving endpoint is bound to Taira chain
  id `fc56984b-2be7-431d-840e-21514d1883f0` and canonical I105 discriminant
  `369` (`0x0171`); the archived pre-v2 Taira chain, generic/default identities,
  and custom address discriminants are not accepted as Taira authorities or
  recipients.


<a id="record-bb0d214b0a3a3c554f15bfd939b4b74253293b85ab2f8e110a661177930acf41"></a>

- The canonical Groth16 BN254 V1 shape is exactly eleven ordered public signals
  (`signal_0` through required `signal_10`), twelve IC points, and a 38-word
  verifying-key ABI preimage. Ten-signal keys, 36-word preimages, and
  compatibility decoders are rejected. Every EVM/TRON destination deployment
  requires typed `outbound_proof_policy` carrying both the semantic proof
  profile and Taira finality anchor; both policy hashes are committed by
  destination and deployment bindings, route hashes, proof requests,
  readbacks, and verifier/policy role-separation checks. The labeled
  signal-binding circuit remains diagnostic-only: production validators reject
  its exact identifier, classification, and artifact digest
  `d7049de0f0b0ecb7ec4f64b885646ab99f85fcbab05dfaf710d3002f17632bb9`
  while requiring the full ordered semantic commitments.


<a id="record-a7328e34910a3283a9a49d2d6675999e489047e912a87d2b2cf6788071aedee4"></a>

- Bridge proofs now own their verifier binding. Native and destination SCCP
  payloads carry a typed historical route-configuration commitment, while
  generic ICS and transparent-ZK payloads retain a distinct verifier-manifest
  role and are rejected by `SubmitBridgeProof` until an authoritative generic
  on-chain verifier exists. SCCP cryptographic finality now compiles mandatory
  BLS public-key, proof-of-possession, quorum, and aggregate-signature checks in
  every build; there is no feature-selected no-verification behavior, and
  structural consistency never substitutes for aggregate-signature
  verification. Historical SCCP commands below that pass `--features bls` are
  obsolete; the first-release crate deliberately exposes no such feature.


<a id="record-676c81b00768bdae75469990f20f03569c1201516cc0a51935c8544266ce3f34"></a>

- Both Torii submit endpoints use one exact two-phase transaction state.
  Preparation omits both `signature_b64` and `transaction_payload_b64` and
  returns the canonical payload plus its signing prehash. Direct submission
  supplies both fields and an explicit positive `creation_time_ms`; Torii
  reconstructs and byte-compares the payload, verifies the authority-bound
  generic signature, and returns a transaction hash. Mixed states, multisig
  direct signing, stale payloads, proof/route drift, unknown or duplicate
  fields, and the retired `manifest_hash_hex` response alias fail closed.


<a id="record-b2264657df796fa8c451107e9c832094476a7795e43b4b33c894031fec0a487d"></a>

- Production EVM, BSC, and TRON deployment precomputes the deterministic route
  address, deploys the immutable wrapped token bound to that route, and then
  deploys the route at the exact precomputed address with the token address.
  Route construction revalidates the token bridge/code/hash binding and keeps
  verifier, semantic-policy, and finality-policy roles distinct. The earlier
  atomic in-route token-construction design is retired.


<a id="record-1f10cd7a9b90b998b363b56598c17a460ccbfef2888bc037b2a6de23dafe1d5d"></a>

- Production release evidence now requires the seven content-addressed
  semantic roles for every profile (circuit, witness generator, verifying key,
  prover build, toolchain lock, honest witness, and honest proof), plus two
  independently signed canonical audit reports that agree on the complete
  artifact inventory and exact eleven-signal claim. The authenticated Rust
  validator rechecks release signatures and identity, canonical-decodes each
  proof, derives the governed signals and full finality anchor, verifies the
  BN254 pairing, and returns a receipt that must exactly match both reports.
  Placeholder, zero, fixture, smoke, cross-role, missing, substituted,
  oversized, or auditor-disagreeing material fails closed.


<a id="record-41c48041320966b7f408ef2a4d6fa81dc988533b5c10932fc7d6f4d23502fa40"></a>

- Every SDK submit path now binds canonical base64 to the exact destination or
  native Norito schema and requires a nonempty, uncompressed, checksum-valid
  frame with zero header padding. Typed SCCP binary reads apply the same exact
  endpoint schema and zero-padding rule. Cross-schema and 1/8/64-byte padding
  adversaries are covered. Current focused corridor validation is green in
  Swift (17/17), Python (114/114), JavaScript source/package distribution
  (124/124), Kotlin/JVM (23/23), and Android Java (two exact harness cases
  covering 23/23 logical SCCP checks); the Windows .NET runner is unavailable
  on this host.
