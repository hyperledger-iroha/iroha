## 2026-05-24 SCCP EVM destination binding material hardening



<a id="record-e5348788463e12c471d87d071b86217a2da5b1b6a173a71f23ccb9a8b3a2f55a"></a>

- The EVM destination-binding tuple is now consistent across Solidity,
  `iroha_sccp`, and Torii: bindings include verifier backend, proof family,
  network id, source/target domains, verifier address, wrapper address,
  verifier bytecode hash, and verifier key hash.


<a id="record-4b8749044f5a360ebf9ecf2ce8812b14298b794d5973154a624576b4b536029f"></a>

- `build_sccp_evm_destination_binding(...)` now fails closed for zero verifier
  or wrapper addresses, missing verifier code hashes, and
  `evm-groth16-bn254-v1` bindings without a non-zero verifier key hash. The
  binding key string includes both hashes for operator inspection.


<a id="record-da93a62dcb3ca53963bf1388c6bdcde2685c6de0b266dcf9cc0afd2f3b887950"></a>

- Torii SCCP artifact/job/proof-submit paths now require
  `verifier_code_hash_hex` for EVM deployment bindings and
  `verifier_key_hash_hex` for EVM Groth16 bindings, preventing stale
  address-only binding hashes from entering relay packages.


<a id="record-10f70e852c5df95bd4409489886d7c4190ef54e94953f090ab36c380f6a8deac"></a>

- EVM Groth16 transparent-proof verification now rejects submission packages
  whose platform deployment binding reuses the generic manifest binding hash,
  even if the binding key is spoofed.


<a id="record-d212999ed28866a609f577b9485323f437eef5100987c9c6445933ee11e7d61a"></a>

- JavaScript and Python Torii client helpers now forward the same production
  EVM destination material for SCCP artifact/job queries; the JavaScript
  package declarations and tracked `dist/toriiClient.js` are synced with the
  source helper behavior.
