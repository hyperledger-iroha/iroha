## 2026-05-28 SCCP EVM live destination evidence collector



<a id="record-c2b0d9171750dff1e5af008cfb4cce3024956e1456e0a8e98e0eb820a763fef5"></a>

- Added `scripts/sccp_evm_live_evidence.py`, a read-only JSON-RPC collector for
  deployed ETH/BSC `SccpMessageBridge` wrappers and Groth16 verifier contracts.


<a id="record-82947345d6fd0436c70a447a4d6dd1a1c4f7e257082471e20db4cf6d192f23b6"></a>

- The helper queries bridge immutable views, checks the live backend/proof
  family hashes, verifies `verifierCodeHash()` against `eth_getCode` runtime
  bytecode, verifies `verifierKeyHash()` against the verifier contract's
  `verifyingKeyHash()`, and recomputes the deployment-specific SORA -> ETH/BSC
  destination binding hash from the live network id, wrapper address, verifier
  address, code hash, and key hash.


<a id="record-1be7387f6b6b2e4550585b38643f0c64d2def66dd5fc265d34e101b31e50fafc"></a>

- With a governed route allowlist hash, the helper renders the same destination
  rollout/route TOML accepted by `scripts/sccp_all_lanes_evidence.py`, including
  the EVM destination network id, bridge address, and binding hash evidence.


<a id="record-ace891beeb61e4059f78e1d115b6436273a01edaee8b39326c9fd56520dca11e"></a>

- Live full-TOML rendering now also requires `--expected-bridge-code-hash` to
  match the bridge wrapper runtime code observed through `eth_getCode`, so
  governance staging cannot rely only on a self-consistent wrapper address and
  view-function tuple.


<a id="record-c260eb1ebc3976b2393eeb6cbd745d251864e0dd138251ea7a615a327f772365"></a>

- Live full-TOML rendering also requires `--expected-network-id` to match the
  bridge wrapper `networkId()`, so the governed EVM lane network id is pinned
  explicitly before rollout TOML is emitted.


<a id="record-ac7c0bd14d30d606e9361cd38b59dca5fb935c6be0549b2b483c3d769d1edccc"></a>

- The live helper now pins `eth_chainId` to the requested SCCP domain before
  considering full TOML complete. ETH defaults to RPC chain id 1 and BSC
  defaults to 56; `--expected-rpc-chain-id` may make that pin explicit but
  cannot override the canonical domain chain id.

## 2026-05-28 SCCP all-lanes destination binding evidence gate



<a id="record-dfb3927c33537bb68022253391b445c75e0fc005e02da31e2ab959db8f445b8d"></a>

- Hardened `scripts/sccp_all_lanes_evidence.py` so destination rollout helper
  comments are preserved as internal evidence metadata instead of being lost by
  TOML parsing.


<a id="record-8a5326268258393e6b36369f0119e0ed79951c30cadd82164d711601db3e0239"></a>

- The all-lanes preflight now requires a supplied destination binding hash for
  every advertised lane, recomputes EVM-family bindings from the helper-emitted
  destination network id and bridge wrapper address plus verifier code/key
  hashes, and recomputes TRON binding hash/key from governed TRON network and
  verifier material.


<a id="record-df987d979eb0d5b1fe28dc341d43e650031e018897c4ea3d8d4f8f3c3c44e0ab"></a>

- `scripts/sccp_evm_destination_evidence.py` TOML output now emits the EVM
  destination network id and bridge wrapper address alongside the binding hash
  in `zk.sccp_destination_rollouts`, with matching comments retained as audit
  hints.


<a id="record-5dedd40bbba1aa1cc2f7b91c6cf1daa8f60b6239307f8d7d475575c2dceff80c"></a>

- `zk.sccp_destination_rollouts` now has explicit
  `destination_network_id`, `destination_bridge_address`,
  `destination_binding_key`, and `destination_binding_hash` fields. SCCP
  production readiness requires the fields needed by each lane: ETH/BSC
  recompute the deployment binding from destination network id, bridge wrapper,
  verifier address, code hash, and Groth16 key hash and require the matching
  canonical binding key/hash; TRON recomputes and requires the canonical binding
  key/hash and matching governed network id; and Solana, TON, and
  EVM/TRON network or bridge-wrapper fields. The ZK consensus policy hash
  commits to them so governed binding evidence cannot drift outside the policy
  digest.

## 2026-05-28 SCCP TRON typed response payload validation



<a id="record-c362161de83fd664bc9dc994af373145af7cbc12a2d55f57fe1a3c6cc47f2cec"></a>

- Hardened Python and JavaScript typed SCCP job/artifact response parsing for
  `TronBase58Check.payload`: response payloads now decode valid TRON
  Base58Check addresses to the canonical 21-byte raw payload hex and also
  accept already-decoded raw `0x41`-prefixed payload hex/bytes. Malformed
  Base58Check text, bad checksums, short payloads, and the all-zero TRON account
  payload now fail during typed response normalization instead of passing
