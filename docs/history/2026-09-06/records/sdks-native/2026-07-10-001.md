## 2026-07-10 confidential-unshield redeem closure for Swift and mobile SDKs



<a id="record-8f7d3747d304f5375ecc1c580dcf197bef5ee1d8d38ef0d7b1874db53af3c1ad"></a>

- Completed the iOS confidential-unshield redeem pipeline. Swift now builds the
  canonical unshield proof and verify requests, verifies the byte-identical
  native proof, validates the exact governed unshield-v3 key and lifecycle
  window, emits the canonical five-field redeem attachment archive (omitting
  the absent trailing default `lane_privacy` field), and exposes an async
  `IrohaSDK` helper for the Torii fetch → proof → verification → attachment
  workflow.


<a id="record-af8534ccf8b29044309d6283c98e98f641031000d2897d57101deae059fde655"></a>

- Torii verifier-key detail responses now include the exact stored
  `VerifyingKeyRecord` as canonical `record_norito_base64`, plus namespace and
  owner metadata. Swift preserves that archive verbatim. Core resolves final
  redeem records with `is_active_at` at the transaction block height, including
  inclusive activation and exclusive withdrawal boundaries.


<a id="record-cded8850817cc3b93b6d7750cfe8f0997b1323a5937502ac7d802e14e39e3950"></a>

- Kotlin/JVM and Android Java now require the exact unshield-v3 verifier
  reference, use canonical marked Iroha prehashes for schema and envelope
  hashes, retain lifecycle metadata, and invoke their existing native unshield
  verifier before returning raw or typed attachments.


<a id="record-1fbea630177416a362dd8b2971d5102268d83639246f0e85152a4bc30418f508"></a>

- Added a focused macOS native E2E lane that builds a temporary
  privacy-production-enabled host bridge, runtime-generates the Rust verifier
  record, proves and verifies a real Swift unshield, and asks Rust to decode and
  cryptographically verify the emitted attachment. Apple production privacy
  packaging remains explicit opt-in; the XCFramework marker and artifact
  manifest boolean must agree, and gated builds use disjoint Cargo target
  directories.
