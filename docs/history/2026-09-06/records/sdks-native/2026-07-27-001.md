## 2026-07-27 native asset holding limits and Python aggregate queries



<a id="record-fe79911b3a3a7dd5add3d74107da1659fdda5b5b3cf8c593319f4a502edb4ea9"></a>

- Added the generic `SetAssetHoldingLimit` ISI and account/asset transfer-control
  record field. Every native forward credit—including transfers, mints,
  DvP/PvP settlement, offline escrow/redemption, and detached balance
  additions, plus balance-scope migration merges—now rejects a destination
  post-credit balance above its configured limit before mutating either side. A
  zero limit can close inbound credit without changing an existing balance. The
  existing transfer-freeze ISI and the new holding limit can be submitted
  together in one atomic transaction draft. Duplicate day/week/month cap
  declarations now reject in native execution instead of depending on
  declaration order.


<a id="record-6993d8e9d1d69b10e047821760d290e6fef022d52cda3441d3d6bbf0a4b6ef6e"></a>

- Added Python instruction/draft/client helpers for transfer freeze, blacklist,
  day/week/month outbound caps, and holding limits; typed aggregate query
  builders; viewer-scoped global transaction queries; and typed
  manifest-trigger declarations plus durable trigger-completion history. The
  aggregate SDK surface mirrors Torii's `count`, `sum`, `min`, `max`, `avg`,
  and `distinct_count` wire contract without inventing transaction effects that
  Torii does not persist.


<a id="record-8758b1f32a2e4c9944fa3c8017e179848840922ff43f1c6f5120c12c44ac9b42"></a>

- Production `cargo check -p iroha_core --lib` passes with the shared exact
  credit primitive and the settlement, offline, detached-delta, and
  balance-scope migration callers. Focused execution of the new holding-limit
  regressions and Orchard KAT is currently blocked during library-test
  compilation by two unrelated dirty-tree fixtures: an unsupported
  `next_back()` call in `privacy_state.rs` and a missing `conditions` field in
  an escrow test record.
