## 2026-06-29 - Localnet 100k Memory Guard Recovery Throttles



<a id="record-9a3f070d01ddb639bdd59406c32758b67503a6bec1680db4cd51d59258eaba4b"></a>

- The latest replay-cap memory guard at
  `/tmp/iroha-oom-repro-20260629-1x100k-replay-cap/memory_guard_report.json`
  reduced cached proposal body rebroadcasts versus the earlier payload-cache
  run, but still tripped the 8 GiB post-load guard at `8,590,131,200` bytes
  total peer RSS. RBC retained bytes stayed below 1 MiB per peer, while logs
  showed the remaining repeat traffic concentrated in targeted RBC READY repair
  across stalled same-height sessions.


<a id="record-ad5a2b216b4fb301a51243190a9999f0fee916b7b0eee3ca4add70d3cf0ada5a"></a>

- After the targeted READY throttle, a fresh release guard at
  `/tmp/iroha-oom-repro-20260629-1x100k-ready-throttle/memory_guard_report.json`
  passed the full 180-second post-load window under the 8 GiB cap:
  `5,892,980,736` bytes peak total RSS, `1,645,428,736` bytes largest peer,
  and only about `292,831,232` bytes of post-load RSS growth. Final queues
  remained intentionally saturated at `1020` transactions / `134,170,800`
  retained bytes, while final RBC store bytes stayed between `141,589` and
  `424,767` bytes per peer.


<a id="record-6b684aec48286ada797f19fe6f97a0d3beb32cdfac9e128a6674fa2d0b4dc539"></a>

- Kept cached proposal replay memory work in place: pending-block canonical
  payload bytes are cached on first borrowed use, cached proposal rebroadcasts
  reuse those bytes, and repeated cached proposal body replay is suppressed
  under relay backpressure after the first targeted recovery attempt.


<a id="record-57f5ac8532aa2c3cb2aa31f4590c4dbbd4e7bd0e7218d7a66ebd8ca3d52852f7"></a>

- Follow-up queue-aware recovery throttling now suppresses repeated cached
  proposal body replay under relay or worker-queue backpressure, slows repeated
  cached proposal body replay under transaction queue count/byte saturation,
  and applies the same transaction-queue-saturated cooldown to repeated
  targeted RBC body and READY repair. First targeted recovery sends still go
  out immediately so a real missing-body or missing-READY gap can heal without
  waiting for the slower recovery cadence.


<a id="record-7176003486d2af3ddb33ed3ce2ec36128ac3af3d934d4ad7d71b17381600bcff"></a>

- The latest guarded release run at
  `/tmp/iroha-oom-repro-20260629-1x100k-targeted-rbc-tx-slow/memory_guard_report.json`
  passed the full 180-second post-load window under the 8 GiB cap:
  `5,772,558,336` bytes peak total RSS, `1,584,234,496` bytes largest peer,
  and `101,548,032` bytes of post-load RSS growth. Final queues still ended at
  the intended cap (`1020` transactions / `134,170,800` retained bytes), with
  `queue_full` admission responses still visible. The 2026-06-29 queue
  pressure operator telemetry and Torii full-queue admission shedding closures
  cover the operator-observability and single-ingress capacity-shed follow-ups;
  any further admission tuning should be driven by new release-gate evidence
  rather than relaxing bounded consensus recovery memory growth.
