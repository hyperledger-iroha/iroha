# Native deterministic game sessions V1

Iroha provides an application-independent multiplayer session protocol. Applications choose an immutable compiled execution-proof profile, opaque application parameters, participant and input limits, admission capability, and payout policy. The native lifecycle does not interpret tracks, cars, physics controls, rankings, or application result bytes. The first compiled adapter implements SORA Cars; additional execution relations reuse the same session instructions and custody rules.

Wallets authorize an exact entry stake and a fresh Ed25519 input key. Input keys sign only session evidence. Any fee-paying transaction account can relay it. Awards remain bound to the original wallet; only that wallet can authorize a different withdrawal destination. There is no contract owner, administrator settlement signature, spending allowance, mandatory relay or trusted result server.

Every compiled stock profile remains **unqualified** until execution-relation, mutation, adversarial multiplayer, four-validator network and release resource gates pass. V1 and V2 are additionally retired from **new session creation** because their recorded-finisher outcome policy could award a racer after a later consensus forfeit. They remain available under their exact original identifiers for historical proof verification and already-created sessions; retirement does not reinterpret those immutable outcomes. The separate V3 stock adapter ranks every forfeited racer below every eligible racer, awards only eligible finish/distance ties or a sole eligible survivor, and refunds when every participant forfeits, even if someone previously finished. V3 preserves the constrained physics state and V2 engine while committing to new outcome rules, adapter source, transcript domain and RCE3 proof wire. All three use the V1 typed manifest, descriptor and envelope schema. Funding fails closed while the selected descriptor is unqualified. Only non-retired profiles can open zero-stake development sessions. A deployed endpoint advertising support alone does not enable entry stakes.

## Generic interface

Registry wire identifiers use `iroha.instruction.v1::game::`.
Every instruction exposes a public Rust `new` constructor and read-only getters, so clients do not need the model's internal `transparent_api` feature to construct the native payloads. Native JSON uses strict adjacent enum tags: unit variants retain explicit null content (`GameAccessV1::Public` uses `public_key:null`; payout policies, phases and RaceTrackV1 use `value:null`). Canonical Norito bytes are unchanged by the JSON spelling. The shared native/browser fixtures include a real browser-shaped prover request and preserve these fields through JSON and framed Norito roundtrips.

| Instruction | Native effect |
| --- | --- |
| `RegisterExecutionProofProfileV1` | Registers the exact immutable compiled descriptor for a known profile; rejects arbitrary uploaded circuits. |
| `VerifyExecutionProofV1` | Verifies a mathematical execution statement and retains a compact verification receipt. This grants no payout authority. |
| `OpenGameSessionV1` | Creates a unique session with immutable manifest, numeric stake asset and amount, and bounded admission height. |
| `JoinGameSessionV1` | The transaction wallet approves the exact manifest hash, asset definition and stake, then pays precisely that stake and registers a distinct input key and opaque application data. |
| `StakeGameItemV1` | An already-joined wallet explicitly reserves one selected NFT before start under its approved manifest; shares the native NFT custody guards with marketplace offers. |
| `StartGameSessionV1` | Any payer starts a full session, or an expired admission window with the manifest's minimum participant count. Creates the actual adapter-defined genesis checkpoint. |
| `CommitGameCheckpointV1` | Relays every original participant's signature over a cumulative checkpoint and optional pending commitment frontier. |
| `ChallengeGameSessionV1` | Relays a current active participant's signed challenge; opens a fixed checkpoint-selection window. |
| `CommitGameInputsV1` | Relays an exact-slot signed commitment during forced progress. |
| `RevealGameInputsV1` | Publishes opaque bounded input bytes and salt matching a retained commitment. |
| `AdvanceGameDeadlineV1` | Permissionlessly advances an expired consensus-height phase. |
| `SettleGameSessionV1` | Verifies the exact selected history and outcome, fixes all awards atomically, and attempts immediate payment. Any blocked payment remains fully backed by custody. |
| `ExpireGameSessionV1` | Fixes exact original-stake refunds for an expired lobby below its minimum participant count, with the same retained claim fallback. |
| `ClaimGamePayoutV1` | Withdraws a positive amount from one outstanding award to the original wallet, or to another existing account authorized by that wallet. |

`GameManifestV1` contains version, application id, proof profile id, opaque application parameters, minimum/maximum participants, batch ticks, maximum ticks, input and participant-data byte limits, access and payout policy. Manifest mutation after opening is impossible. Platform ceilings are 32 participants, 4,096 input/data bytes per participant, 65,536 parameter bytes, 256 ticks per batch, 1,000,000 ticks and 4,096 batches. The product of batch count, participant count and per-input bound cannot exceed 4 MiB of retained raw inputs. Each compiled relation imposes additional constraints.

`GameOutcomeV1` contains terminal tick, ordered winner slots and opaque result bytes. `NoPayout` requires zero stake; `EqualWinnersOrRefund` divides the pool among verified winners and returns original stakes when there are none. The profile verifies application result semantics and their projection to winner slots.

The generic proof statement binds exact NetworkId, session id, manifest hash, roster hash, transcript root, dispute root and outcome hash. A mathematical verification receipt is deliberately separate from permission to settle a funded session.

## Discovery and authentication

`FindGameSessionById` is the typed singular query. Public routes are `GET /v1/games/capabilities`, `GET /v1/games/sessions?cursor=<exclusive-hash>` (optional `application_id` and `profile_id` filters) and `GET /v1/games/sessions/{session_id}`. A list scans at most 128 state keys and returns at most 32 public summaries. Capabilities include current consensus height, network id, fee-asset identifier, compiled profile descriptors, explicit `new_session_profile_ids`, and platform bounds. Creation must use an exact profile in that admission list; absence does not permit a legacy creation fallback. Historical verification and settlement discovery still use the complete retained descriptor catalog. `execution_transport_ready` checks this endpoint's actual Torii body, ledger transaction, Connect frame/buffer and P2P Connect/transaction-gossip caps against the bounded execution corridor. Missing required local services or any undersized cap returns false. This flag neither qualifies a proof nor authenticates other validators' transport settings; it is a browser readiness check and is never used by consensus instructions. Ordinary Torii JSON remains node evidence until a client authenticates ledger finality.

`GameSessionEventV1` carries session id, revision, phase, selected dispute root and exact per-slot payout claims. Full records retain the manifest, participants, checkpoint, forced history, liability, payout claims and terminal outcome; public summaries expose the outstanding liability and claims too. Invitation sessions are omitted from discovery; their direct ledger records remain publicly verifiable.

Private admission uses `GameAccessV1::Invite(PublicKey)`. The invitation key signs a digest of session id, paying wallet, input key and participant data. The wallet separately signs its stake transaction. A disclosed invitation signature cannot be reused by another wallet or with substituted input authority. Applications may distribute the invitation key in a URL fragment; it has no wallet-spending power.

## Explicit indivisible item stakes

`JoinGameSessionV1` requires `expected_manifest_hash`, `expected_asset_definition` and `expected_stake` in the wallet-signed payload, including a zero stake for free sessions. Native admission compares all three to the immutable session before any balance, liability, roster or index mutation. Endpoint-provided lobby text cannot authorize a larger debit or a different asset. Missing terms reject decoding; the undeployed four-field encoding has no unbounded-debit fallback.

`StakeGameItemV1 {session_id, nft_id, expected_manifest_hash}` authenticates the already-joined slot's wallet, requires the exact approved manifest and open admission window, and permits one NFT per permanent slot. Joining and staking may be instructions in the same canonical wallet transaction. The NFT must belong to that wallet; a domain owner's broader ordinary transfer permission cannot authorize this deposit. The execution profile must be qualified even if the session's fungible stake is zero. No item can be deposited after start, and later entrants can inspect the sorted `item_stakes` in the native session before joining.

The V1 indivisible-item policy is fixed: exactly one proved winner receives all explicitly staked NFTs. Multiple exact winners, no eligible winner, or an unstartable lobby cancellation return each item to its original owner. There is no recipient field in a submitted result that can override this rule. This policy does not change the fungible pool's equal-tie split. `GameItemStakeV1 {slot, nft_id, custody, metadata_hash, recipient, claimed}` exposes the exact original selection and subsequent completed native transfer. Before a terminal decision, recipient is absent and claimed is false. Native release preflights the complete bounded NFT batch, including shared reference-count decrements, before any associated payout. All NFT transfers and terminal record changes are atomic.

Item metadata is frozen while reserved. Generic NFT transfer, metadata edits, unregister, domain cascade, account removal/rekey and another protocol's custody release cannot change the reservation. Before accepting an item, native admission verifies that every previously joined wallet still exists. All possible winner wallets then remain retained while items are at stake, including zero-XOR sessions, so deleting a non-staking winner's account cannot veto settlement. Snapshot restoration rejects absent custody and any absent retained participant or claim owner. Custody records remain permanent after release, and restore cross-checks both directions between exact game items and shared reservations.

The manifest and application's participant bytes remain unchanged. A nonempty item selection enters a domain-separated `roster-with-items` commitment over session id, original participants and original item records. Removed-participant markers, terminal recipients and claimed flags are normalized away. Sessions without items retain the existing `roster` commitment bytes. Native settlement rederives the composite commitment from ledger state before comparing the proof. The execution proof binds the opaque 32-byte roster commitment in its public statement and Fiat–Shamir transcript; the RaceV1 relation and its wire size are unchanged.

## Signed live progress and disputes

The generic message prefix is `iroha:game:session:v1\0`, followed by exact NetworkId, domain and canonical compact-Norito body. Domains distinguish invitations, checkpoints, commitment sets, individual commitments, reveals, manifests, outcomes and dispute history.

Before disclosing a batch, all original participants sign the same complete commitment-set body. A cumulative checkpoint signs the input-transcript and simulation-state roots. The generic transcript consists of ordered batches `{start_tick, inputs:[opaque bytes per slot]}` and ordered removal events `{tick, slots}`. Simulation-state roots hash an opaque canonical adapter-state byte vector. The adapter checks application meaning and execution-proof constraints.

A challenge opens 30 consensus blocks for the highest certified checkpoint and pending frontier. A retained same-tick frontier cannot be discarded or replaced. A terminal certificate submitted during selection does not shorten the window. Once selection closes, its prefix is fixed; a valid proof for another history cannot settle this session.

Forced commitment and reveal phases each provide 15 consensus blocks. Anybody can make a retained reveal available. Only an expired native deadline removes an absent participant from future input authority. The removal tick and opaque selected inputs are retained for the adapter to prove. Completed application achievements are interpreted by the relation, not by peer assertions.

Whenever absence removes an input authority, the last certified transcript prefix becomes an immutable anchor. Proofs must match every anchor, so later signers cannot rewrite a departed participant's input history.

Every resolved batch increments the epoch. Live progress can resume only with a jointly signed checkpoint at the exact end of a newly completed forced batch, newer than the retained checkpoint and in the new epoch. A pre-dispute checkpoint cannot replay to restart deadlines. Published forced commitments must resolve before resumption. Optional checkpoints and frontiers always need all original input keys, including removed participants. An absent key can prevent live certificate resumption but cannot prevent bounded forced progress or proof settlement. This prevents remaining keys from pinning a deliberately unprovable checkpoint over a departed winner.

Dropping below the manifest's minimum active participant count moves native state to proof submission. The adapter must prove the resulting outcome. In SORA Cars, a sole survivor receives a technical win only when no participant already finished first; no timeout shortcut pays an unchecked claim.

## Custody and qualification

Custody uses a non-signing derived public key and a session-specific domain. V1 stakes require a globally scoped fungible asset: the manifest does not yet freeze a dataspace balance scope. Creation, positive-stake joining and funded snapshot restoration reject dataspace-restricted assets. The browser pins its intended XOR asset separately. New custody must be empty. Only the exact native wallet-authorized entry transfer may credit retained custody; unsolicited transfers, minting and generic credits are rejected so an enormous deposit cannot make fractional withdrawals unrepresentable. Generic transfers, burns and unrelated escrows cannot debit native custody, including closed sessions.

Private one-shot movement capabilities bind funding, proved awards and later withdrawals to their exact retained session. Wallet removal/rekey and asset-definition removal remain blocked while outstanding stakes or claims depend on them. Domain deletion checks its indexed asset definitions before any cascade mutation, so it cannot bypass those retained reserves. A paid winner no longer retains a wallet reference merely because a different winner still has an unpaid claim. Custody identities remain reserved after all payments. Exact custody indexes and bounded wallet/asset reference counters make these guards independent of total retained game history; skipped indexes are rebuilt and checked from authoritative session records on load. Rebuild rejects duplicate participant wallet or input authorities, invalid custody, excessive payout precision, incorrect active liabilities, and claims inconsistent with the immutable proved awards. A closed liability must equal the sum of outstanding claim amounts. Restored sessions must belong to the node's network. A failed rebuild does not publish a partial index. Zero-stake sessions skip transfers but still require an existing participant account and reject custody itself as a participant.

A session fixes its terminal awards once, only after history-bound execution proof verification. Once checkpoint selection is sealed, a terminal proof may settle during either forced phase as well as the explicit proof phase. Unused controls after a proved terminal tick cannot require continued play or a final signature. A post-start timeout cannot refund away another participant's provable outcome. No-winner refunds and tied payouts are determined by the verified outcome and immutable policy. Refunds return each original stake exactly. The session freezes payout precision at admission: the asset's fixed scale, or the protocol maximum of 28 decimal places for an unrestricted asset. Tied winners receive floor-rounded equal shares at that quantum. Any remaining atomic units are distributed one each in increasing permanent winner-slot order, so awards differ by at most one indivisible unit and exhaust the exact pool without a house fee. Admission checks every bounded roster/winner count for representable pools and payouts before funding, including large unrestricted quantities. No later asset lookup chooses a new rounding policy.

`GamePayoutClaimV1 {slot, amount, remaining}` records each nonzero award in increasing permanent slot order. `amount` is immutable; `remaining` can only decrease through a successful exact withdrawal. If the complete initial batch passes existing asset controls and checked destination arithmetic, all payments occur atomically and remaining amounts are zero. Otherwise the native result still settles, no payment leg is applied, and the complete backed claims remain in custody. Mutable issuer outgoing controls, incoming restrictions, holding limits and Numeric destination overflow cannot change a proved award or veto terminal result recording; they may still prevent an actual withdrawal until its destination or restriction changes. Settlement status therefore denotes a finalized result and award entitlement, and does not by itself mean every wallet has been paid.

`ClaimGamePayoutV1 {session_id, slot, destination, amount}` permits anyone to retry a positive amount to the original wallet. Redirecting to another existing account requires that original wallet's transaction authority; the gameplay input key has no such permission. Partial withdrawal can avoid destination overflow without withholding another winner's payment. Every claim still respects the asset's current transfer controls. The closed session's liability remains the sum of `remaining`, and custody protection and relevant account/asset references persist until that sum is zero. A failed claim cannot consume entitlement or reduce reserves.

Every settled session records `verification_id` and `settled_at_height`. The latter identifies the settlement block; the receipt identifies the first mathematical verification and can predate settlement. `FindExecutionProofVerificationById` and `GET /v1/games/verifications/{verification_id}` return one bounded receipt `{profile_id, statement_hash, proof_hash, verified_at_height}`. The receipt's canonical envelope remains in its finalized verification transaction, discoverable at `verified_at_height` and authenticated by its hash; it is not duplicated into every state response. A stand-alone verification receipt proves mathematical validity only. Settlement still performs complete native session-history checks before any payout.

Core adversarial tests cover missing, duplicate, stale and wrong-domain signatures; preserved pending inputs; fixed challenge deadlines; forced progress and participant removal; custody retention, burn and unrelated-escrow bypasses, reference-count overflow and restored-index integrity; disabled funding; invitation replay; and checkpoint replay prevention. A four-state deterministic replay unit test is not a four-validator network qualification run. Live-stake release additionally requires actual validator finality/dispute/settlement runs, independently authenticated proof-and-ledger verification bundles, clear browser trust labels, semantic proof mutation tests and bounded proof time, verification time, memory, payload and gas evidence.

The four-validator release test compares two separate surfaces at an identical committed height: an independently authenticated finality artifact covering the execution-witness commitment, and the locally retained complete WSV checkpoint. The feature-gated, read-only `Kura::local_wsv_checkpoint_hash_for_tests` uses the existing bounded native checkpoint and commit-manifest codecs, requires their exact height/block/digest/artifact bindings, and returns no result while publication is incomplete. The canonical WSV hash covers serialized consensus World records, including sessions, assets, proof receipts and NFT custody; only bootstrap and topology caches are excluded. Equal local WSV hashes establish local test convergence and must not be described as a publicly quorum-signed full-state root. The four-validator run remains a required release gate.
