# Iroha security-audit closeout matrix

This matrix records the source-level disposition of the 21 security findings
approved for the first-release remediation. It identifies the enforcing code
and the regressions that make each disposition reviewable. It is not, by
itself, a release-qualification receipt: the final section separates evidence
that exists in the tree from validation that must be rerun on one settled
candidate.

The remediation deliberately uses fresh-genesis schema cuts. Contract
lifecycle state, moderation economics, ISO records and replay tombstones,
route-authentication metadata, and affected Norito fixtures are not inferred
or migrated from ambiguous legacy values.

## Qualification boundary

The rows above mean that an enforcing source path and reviewable regression are
present for all 21 findings. They do not claim that the current shared working
tree, an arbitrary dirty build, or an earlier commit passed the final release
corridor.

Release qualification must be collected from one settled candidate and must
record the exact commands and results for formatting, focused crate checks and
tests, codec/source guards, generated OpenAPI and route-catalog equality, SDK
parity suites, relevant four-validator integration scenarios, strict
all-target Clippy, and the workspace test gate. A timed-out, blocked, or
deferred command is recorded as such and is not a pass. Documentation route and
translation parity must be validated in the sibling `iroha-docs` checkout.
`Cargo.lock` is outside this remediation and must remain byte-for-byte
unchanged.
