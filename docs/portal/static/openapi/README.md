OpenAPI signing
---------------

- Release Torii OpenAPI specs (`torii.json`) use the hard-cut manifest contract `version: 2` and must be signed. The manifest is verified by `cargo run -p xtask --bin xtask -- openapi-verify`; V1 manifests, legacy field aliases, and unknown fields are rejected.
- First-release development snapshots may carry an unsigned manifest only when CI passes `--allow-unsigned`; both the Rust verifier and portal-side Node consumers recompute the exact `torii.json` path, size, SHA-256, and BLAKE3 digest, but skip the Ed25519 signature check.
- Generator provenance is explicit. `generated_unix_ms` is the source commit timestamp in milliseconds, so regenerating an identical source state is reproducible. Every manifest records `generator_source_sha256_hex`. For a clean manifest, that digest is a domain-separated SHA-256 over `release/openapi-generator-inputs-v1.txt` plus the canonical `git ls-tree` bytes for its exact paths. The inventory binds the Torii generator closure, workflow and portal tooling, release version map and package sources, every maintained SDK tree, and the Android codegen hash/metadata records. Clean manifests also record the real lowercase 40-hex source commit and set `generator_dirty` to `false`. A dirty unsigned development snapshot instead sets `generator_commit` to `null`, sets `generator_dirty` to `true`, and records a deterministic digest of all non-generated tracked and untracked source state anchored to that committed input-tree digest. Canonical OpenAPI outputs, manifests, `versions.json`, and an explicitly requested signing-payload output are excluded from dirty-state hashing.
- Dirty provenance is development-only: the generator refuses to sign it, and release verification rejects it even if a signature is injected into the manifest. Commit or clean the source changes and regenerate before signing a release artifact.
- `ci/check_openapi_spec.sh` is the clean pinned-input release gate. A manifest is generated at a clean source commit and checked in by a later output-only commit, so `generator_commit` must resolve to a real ancestor of the output-bearing `HEAD`; it is never forced to equal `HEAD`. The gate recomputes the canonical input-tree digest at both commits and requires both to equal the signed manifest value. It also requires byte-identical root/current specs and manifests, validates `versions.json` and `release/version-map.toml`, compares two independent generator passes, and compares two independent release-input and version-map summaries. Any SDK, package-version source, codegen record, generator, workflow, or release checker drift invalidates the manifest. `OPENAPI_REQUIRE_SIGNED=0` relaxes only the detached-signature requirement; it never admits `generator_dirty`.
- The checked-in `allowed_signers.json` intentionally contains an empty `allow` array. This is a valid version-1, fail-closed trust root: unsigned development snapshots still require their explicit opt-in, while every signed artifact is rejected because no release signer is provisioned.
- Production release operators must provision a separate version-1 allowlist containing only operator-held Ed25519 public keys, then pass it to portal sync with `--allowed-signers=<path>` and run `ci/check_openapi_spec.sh` with both `OPENAPI_REQUIRE_SIGNED=1` and `OPENAPI_ALLOWED_SIGNERS_FILE=<path>`. The allowlist is bounded, duplicate-free, strict-schema JSON; keys and algorithm labels must be canonical lowercase Ed25519 material, and the file must not be a symlink, hard link, or group/world-writable. Signed mode rejects unsigned root/latest/current artifacts; the immutable unsigned `2025-q2` development snapshot remains an explicit historical exception. Never use a public fixture, example, or deterministically documented key as a release trust root.
- The canonical `xtask` dependency compiles Torii's supported documentation profile (`app_api`, `telemetry`, `profiling`, `schema`, `p2p_ws`, `connect`, `zk-verify-batch`, and `push`). The generated operation set is the exact enabled `RouteCatalog` OpenAPI projection; do not hand-add disabled or uncataloged paths to a snapshot.
- Local private-key signing is intentionally unavailable. Release signing is detached-only so the Ed25519 private key remains in PKCS#11/HSM custody. To re-sign after a key rotation:
  1. Update the separately provisioned operator allowlist with the new public key; do not add production keys to the checked-in empty allowlist.
  2. Commit the complete generator-input inventory first. At that clean pinned source commit, emit the unsigned manifest and deterministic signing bytes: `NORITO_SKIP_BINDINGS_SYNC=1 cargo run --locked --offline -p xtask --bin xtask -- openapi --output docs/portal/static/openapi/torii.json --unsigned-manifest --signing-payload <operator-staging>/openapi-manifest-v2.payload`.
  3. Have the release HSM sign the exact payload file with Ed25519 and export only `{"algorithm":"ed25519","public_key_hex":"...","signature_hex":"..."}`. The payload is a domain-separated, fixed-order TLV encoding of the V2 version, timestamp, clean/dirty provenance, source digest, artifact path, byte count, SHA-256, BLAKE3, and the raw `torii.json` bytes.
  4. Regenerate from the same clean source state and attach the envelope: `NORITO_SKIP_BINDINGS_SYNC=1 cargo run --locked --offline -p xtask --bin xtask -- openapi --output docs/portal/static/openapi/torii.json --signature-envelope <signature-envelope-json>`. The envelope is verified against the reconstructed TLV payload before `manifest.json` is written.
  5. Run `npm run sync-openapi -- --allowed-signers=<operator-allowlist-path>`, commit only the generated OpenAPI outputs/index in the output-bearing commit, then run `OPENAPI_REQUIRE_SIGNED=1 OPENAPI_ALLOWED_SIGNERS_FILE=<operator-allowlist-path> bash ci/check_openapi_spec.sh`. The gate confirms that the ancestor source pin, current release inputs, both checked copies and maps, deterministic regeneration, signature, and provisioned trust root all agree.
- `artifact.path` is always relative to the directory containing its manifest. The canonical value is `torii.json`; sync copies the manifest byte-for-byte into version directories and never rewrites signed fields.
- For unsigned first-release snapshots, use `NORITO_SKIP_BINDINGS_SYNC=1 cargo run --locked --offline -p xtask --bin xtask -- openapi --output docs/portal/static/openapi/torii.json --unsigned-manifest`, then run `npm run sync-openapi -- --allow-unsigned` from `docs/portal`.
- Sync stages and validates the complete prospective artifact tree and version index before the first tracked write. The `versions.json` root and entry objects have an exact duplicate-free V1 schema; unknown fields, pre-release aliases, and misspelled metadata are rejected by generation, parity verification, and signature checking. Rust and Node consumers read bounded inputs through pinned no-follow descriptors, reject symlinks and multiple hard links, and detect in-place mutation; publication uses synced same-directory temporary files and atomic replacement, with the version index written last. Existing non-`current` version directories are immutable; create a new label for each release. Unchanged entries retain their recorded `updatedAt`, while changed entries derive it from the validated manifest timestamp, so filesystem mtimes cannot rewrite historical metadata.
