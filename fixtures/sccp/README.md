# SCCP fixtures

Shared SCCP v1 vectors (`specs/sccp.md` §11). They are generated by Rust, by
the independent Python reference (`scripts/sccp_reference/`) or by the
contracts themselves, and consumed by the contract suites (EDR, Acton), the
node and the SDKs.

Conventions of the Rust-generated files: byte strings are `0x`-prefixed
lowercase hex; integers that can reach `2^53` or more (`u128` amounts,
`ton_amount_bound`) are decimal strings and every other integer is a JSON
number; rejected inputs name the `iroha_sccp::v1` error variant that rejects
them (for example `TrailingBytes`, `BadS` or `BadOffset`).

## Rust-generated v1 vectors

These files still follow revision 4 until `iroha_sccp::v1` implements
revision 5. `crates/iroha_sccp/tests/v1_vectors.rs` regenerates them from
`iroha_sccp::v1` and fails when a committed file differs. Each generator also
runs the crate's verifiers over its own vectors (Merkle and history paths,
signature sets, roster rotation, message and control proof bundles), so every
committed vector is accepted or rejected by the Rust implementation exactly as
recorded.

| File | Content |
|---|---|
| `payload_v1.json` | The five profiles (tag, domain, identity word, `network_bytes`, route id, account codec); payloads for all 8 directions with `deadline_ms`, payload hashes, lane bytes and message ids (§3.2, §3.3); `taira_units` conversions and rejected amounts (§0); rejected payload encodings covering every §3.1/§3.2 rule |
| `commitment_tree_v1.json` | 512 mixed transfer/control leaves (`leaf_rule`), worked transfer, control and node preimages, roots and every path for counts 1..=17 and 512 including promoted nodes, and confusion negatives (internal node as leaf, transfer leaf at a control position, flipped pause, count and path mismatches) |
| `history_v1.json` | 40 history leaves (`leaf_rule`), and for sizes 1..=40 the root, the right-bagged peaks and every path (§3.5) |
| `eip712_v1.json` | Domain separator for the fixed `NetworkId`; attestation, rotation attestation and key-PoP struct hashes and digests; four fixed bridge keys with low-S signatures; high-S, `s = HALF_N + 1`, `v ∉ {27, 28}`, `r`/`s` range negatives; a signature checked against another digest; the forced recovery-id ≥ 2 re-sign with fixed extra entropy (§3.6, §3.8) |
| `roster_v1.json` | Roster preimages and digests for n = 4, 7 and 31 with zero slots; `t` for every n in 4..=31; ordering, size, threshold, generation and packing negatives; the §5.1.5 validity bounds at every boundary |
| `evm_calldata_v1.json` | A coherent scenario (rosters g7 and g8, attestations of heights 100, 150 (rotation) and 200, signature sets, block and history roots) and the golden calldata of `finalizeFromTaira`, `finalizeFromTairaHistorical`, `rotateRosters`, `applyControl`, `applyControlHistorical`, `voidExpired`, `voidExpiredHistorical`, `voidFrozen` and `transferToTaira`; every §5.2.2 selector and event topic; the view calls and the `rosterState()` return; `SccpTransferToTaira` and `SccpVoided` logs; `calldata_conformance`, the shared void and burn calldata table of `voidExpired`, `voidExpiredHistorical`, `voidFrozen` and `transferToTaira` (canonical, trailing byte and word, truncation, a dirty high bit in every `uint8`/`uint32`/`uint64` field, every dynamic offset moved past an inserted word, nonzero padding of every `bytes`, recipient length and amount bounds, `voidFrozen` counts 0/1/256/257 and the `2^64` end) where each entry records the Rust decoder's verdict (`accept` or the `AbiError`) and the contract's (`accept`, the custom error, or `empty` for a revert in Solidity's ABI decoder), and both accept exactly the same entries (`contracts/evm/sccp/test/sccp_v1_fixtures.test.js` replays it under chain ids 1, 56 and `0x2b6653dc`) |

Common inputs: the Taira `NetworkId` is `0x11…11` (the §3.4 example value),
the base time is `1 800 000 000 000` ms and outbound deadlines are one day
later, and fixture bridge key `i` has secret
`keccak256("SCCP/FIXTURE/KEY/V1" ‖ u8 i)`. Codec-3 (`taira_account`) fields
are opaque byte strings; contracts check only their length (§3.1). The EVM
destination word is `word(0x22…22)`.

Regenerate after a reviewed layout change, then review the diff:

```text
scripts/cargo_fast.sh --target-slot sccp --stable-local-metadata --incremental -- \
  test -p iroha_sccp --test v1_vectors -- --ignored regenerate_v1_vectors
```

`native_transfer_event_v1.json` holds the inbound transfer and void vectors
of every source: the `SccpTransferToTaira` and `SccpVoided` logs (Ethereum,
BSC), the `transferToTaira` and `voidFrozen` calls with their `0x41` contract
and owner (TRON), and the `sccp_transfer_to_taira` external-out body `BoC`
with its minter (TON), each with the normalized event Taira derives.
`crates/iroha_sccp/tests/ethereum_light_client.rs` regenerates it with
`--ignored regenerate_native_transfer_event_v1` and runs the Ethereum, TRON
and TON vectors through their light clients.

`governance_v1.json` and `ton_bodies_v1.json` of the §11 table are added with
the governance payload and TON message-body code that generate them.

## Python reference vectors (revision 5)

`scripts/sccp_reference/` is an independent, dependency-free Python
re-derivation of the contract-visible relation of `specs/sccp.md` revision 5:
Keccak-256, BLS12-381 with the optimal ate pairing, RFC 9380 hash-to-G2 under
`DST_SIG`, the min-pk proof-of-possession signatures, payloads and message
ids, transfer and 199-byte control leaves, the promote-odd tree and the
history accumulator, the 221-byte finality header `X` (X1–X7 and the inactive
form), `R`, the 116-byte `QC_FIXED`, the 165-byte Commit preimage `P`,
committee roots, checkpoint ids, anchors and forgery evidence ids, and an
executable model of the §5.1 destination state machine. It writes:

| File | Content |
|---|---|
| `finality_v1.json` | The §11.2 worked examples (every pinned value is asserted while building); valid headers and one negative per invariant X1–X7 and length; `result_of_preimage` bounds; signer-bitmap encodings; the §11.3 test keys (`sk_i = KeyGen(SHA-256("sccp-finality-test-ikm" ‖ u8 i))`, i = 0..34) and committees n = 4, 7, 31; full certificates (lowest, highest and scattered q signers including {0, 9, 30} at n = 31; key-change and heartbeat rotations) with `R`, `P`, `m`, `hash_to_G2(m)`, the aggregate key and signature in compressed (TON), 192-byte EVM and EIP-2537 forms, the 768-byte pairing input, the EVM `TairaCertificateV1` calldata and the TON cell contents; negative certificates (kind `0x02`, popcount q ± 1, spare bits, retired QC extension bytes, wrong `I`, network or DST, a signed height mismatch, a tampered `X`, dirty `X` for every invariant, past generation, foreign root, committee-root mismatch, signer `y` with a wrong sign, `y ≥ p` or off curve, key flags, `σ` outside the subgroup, zero, each limb `≥ p`, `c0`/`c1` swapped, off curve, raw-bitmap and MSB-first `signers`, exact lengths), each with its EVM and TON outcome. The popcount and spare-bit rows carry exactly `48q` bytes of `signerYs`, so EVM reaches the step 5 bitmap check instead of the step 1 length check; the TON form splits `QC_FIXED` into `qc_fixed_cell` (all but the last 4 bytes) and `signers`, so a length negative is a malformed cell |
| `committee_transitions_v1.json` | The §11.1 state-machine rows as scenarios: a deployment and its initial state, then calls with `now_ms`, each with the expected outcome, events and `state_after` (initial pin, checkpoints and `high`, key-change, heartbeat and lowered-validity rotations, a successor already expired, 16 batched rotations and `TooManyCertificates`, K→K′→K, a future-dated certificate replayed across validity periods, forged heights after the genuine end then the V3 latch, old generations refused, V1/V2/V3 with their nearest neighbours, expiry then refusal then `voidFrozen`, a latch inside a batch, inline `LatchRequired` then a latch, a future-dated rotation, finalization with inline and checkpoint proofs, history proofs, supply cap and voids, and the TON `next_keys` and checkpoint-eviction rows). Certificates are pooled and referenced by id; `ton_replayable` marks EVM scenarios a TON harness replays unchanged. The file also pins every §5.2.2 selector and event topic (recomputed and asserted) and the §5.2.2 error-name → TON exit-code table that the outcome names key on |
| `control_v1.json` | The four §3.4 control-leaf examples (asserted) with their 199-byte preimages and TON builders; leaves for every target network, both tracks and both pause values; constraint and recording negatives; the `SccpControlApplied` topic; destination-effect scenarios with full proofs (Parliament and fast pause in both orders, a fast pause delivered after its expiry, stale, equal and gapped nonces, the `MAX_FAST_PAUSE_MS` clamp, local expiry, resume, a historical control proof, and controls of another network, Taira network, revision or destination, a transfer leaf offered as a control and a recorded leaf violating a constraint). Its Taira blocks are synthetic destination inputs, so control nonces need not follow Taira's dense per-revision sequence |
| `bls_consensus_v1.json` | RFC 9380 `expand_message_xmd` and hash-to-G2 vectors (imported and reproduced); hash-to-G2 traces under `DST_SIG` with the EIP-2537 `MAP_FP2_TO_G2` inputs and outputs; `KeyGen`, `Sign` and `Verify` with negatives (identity, non-subgroup, non-canonical encodings, wrong DST); `FastAggregateVerify` and `AggregateVerify`; the consensus preimage allowlist with every row one byte short and one byte long, flag and wrong-kind neighbours; the ethereum/bls12-381-tests standard inputs under `DST_SIG`; and a captured Ethereum mainnet sync-committee aggregate (502 signers, from `rpc/eth/`) verified under the same ciphersuite |

Conventions: byte strings are `0x`-prefixed lowercase hex, field elements are
`0x` hex integers, `u128` amounts and nonces passed to `voidFrozen` are
decimal strings, and every other integer is a JSON number. Outcomes are `ok`
or a §5.2.2 error name; a latch or a lost `Live` inside `submitCheckpoints` is
`ok` with `stopped`. Where the specification names no error the files record
the reference choice under `error_choices` (not `Live`: `Equivocated` when
latched, `CommitteeNotAccepted` when expired; signer-key encodings:
`BadCommittee`; signature encodings and pairing: `BadSignature`; the
`voidFrozen` range: `BadAmount` on EVM, `BadRange` on TON; the check order is recorded as `check_order`). The model takes the
optional cheap path (§5.1.3 step 8), so `SccpCertificate` appears only on full
verifications. The Taira `NetworkId` is `0x11…11`, `I` is `0x77…77` and the
EVM destination word is `word(0x22…22)`.

Regenerate after a reviewed change and review the diff; `--check` (the
default) fails on drift, and `pytest pytests/scripts/test_sccp_reference.py`
runs the same drift check together with the cross-checks (RFC 9380, the
ethereum/bls12-381-tests inputs, the captured mainnet aggregate, values from
`blst`, the Rust `payload_v1.json`, `commitment_tree_v1.json` and
`history_v1.json`, and `bls_consensus_rust_v1.json` when present):

```text
python3 scripts/sccp_reference/generate.py --write
python3 scripts/sccp_reference/generate.py --check
```

## Contract-generated vectors

`ton_stateinit_v1.json` is emitted by the Tolk contracts
(`contracts/ton/sccp/scripts/stateinit-golden.tolk`) and cross-checked by
`scripts/generate_ton_sccp_stateinit_golden.py` (§5.3.1). It pins the
canonical minter initial data, the minter, bucket (canonical, not activated)
and wallet addresses and the code cell hashes and depths. The Rust
`iroha_sccp::v1::ton_cell` unit tests recompute every vector from the recorded
code references and pin the `n4` values; `iroha_sccp::v1::roster` pins the
`n4` roster digest.
