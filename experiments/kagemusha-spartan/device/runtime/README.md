# Experimental device runtime fixture

This standalone crate links the current canonical Rust provider and complete experimental engine. It is installed only in disposable test application namespaces. Its public fixture issuer keys and synthetic ledger events cannot select production funds.

`./build-apple.sh` builds the real iPhone static archive in the persistent `target/aarch64-apple-ios/release/` lane. The explicit iOS 18 deployment floor applies to Rust and C dependencies. The Apple app project lives in `../ios/runtime-project.yml`; it consumes `SPARTAN_DEVICE_ARCHIVE` and `SPARTAN_DEVICE_ARTIFACTS`. The C callbacks are specified in `spartan_device_fixture.h`.

The final host recursive-chain test emits `program-bundle.norito`, `parameter-manifest.norito`, and `parameter-signature.bin` when `KAGEMUSHA_SPARTAN_DEVICE_ARTIFACTS` names an output directory. They contain the actual eight fixed-point verifier programs and independent fixture-root authentication. No placeholder artifact is accepted.

The run performs real native enrollment custody and existing Ed25519 account admission, actual hardware Bootstrap, restart recovery, a fixture-genesis BLS-certified synthetic Load100 event, and a Send10 to the fixture's software counterparty wallet B (B signs the Request), confirmed through the platform authentication UI. B then Bootstraps, verifies and Receives that Payment, and pays the same 10 back under a Request signed by this wallet's hardware key through the canonical Request domain. The return Payment is retained in `incoming-payment.bin`, and the launch that proved B's operations stops there (report `stage 1 of 2`): B's proving leaves memory resident that a receiving phone would not hold. The next launch, a fresh process, performs this wallet's Receive from the retained bytes to a verified, durable output in platform custody; that is the measured operation. The completed-Request relation refuses payer == receiver, so the earlier self-transfer cannot be prepared. B's key is a public fixture scalar and B has no platform custody; its three operations are proved in the same process by the same engine and installed programs and are measured separately (`Counterparty*`). Each custody operation checks retained custody before preparing. Re-running after process termination must return the same retained Payments without another Send. After the Receive, a new owner of the same custody (fresh parameter authentication, provider, runtime, C session and account admission, as after a process restart) must return the Receive's exact completion and the exact outgoing Payment through the C output entry, and the verified new head must show the credit and an unchanged burned total: Native admission burns a Payment it cannot credit instead of refusing the Receive. The generated `complete-payment.bin` (this wallet's outgoing Payment) and `incoming-payment.bin` are complete peer objects; their actual sizes are reported separately from performance or qualification claims. `device-measurements.json` (schema v2) records every phase's wall time and its own peak RSS: exact on Linux/Android (VmHWM reset before the phase), a 5 ms sample maximum elsewhere (`phase_peak_method`; one extra fixture thread). Phases named `*_drill` are fixture checks; `receive_normal_flow_us` is the observed Receive minus its drills and measurement overhead.

Host run (Mac or Linux, software P-256 keys from the canonical simulator, no user confirmation): `KAGEMUSHA_SPARTAN_DEVICE_ARTIFACTS=<bundle dir> KAGEMUSHA_SPARTAN_DEVICE_ROOT=<new empty dir> cargo test --offline --release --lib -- --ignored --nocapture two_wallet_device_flow_on_host`. It makes the same three launches as a phone run: stage 1, the measured Receive, then a launch on the same custody that must return every output retained, with no new execution or confirmation. `device-measurements-launch-N.json` keeps each launch's record.

After fixture-root parameter authentication, the same exclusive provider enters the real bridge registry and Session through an isolated test-only constructor. Account admission and every monetary operation then call the eight production C exports, with actual C output allocation/free, close rejection, unused-review discard, exact execute-reply retry, and retained-output checks. The fixture also rejects stale preparation on repeated launches. This exercises C dispatch on both phones; the Android entry uses JNI to reach that fixture. It does not exercise the production `NativeWalletRuntime` installation-to-experimental-owner transfer, nor claim that the fixed test issuer is a production installation authority. A separate native proof reader shares the immutable authenticated parameters to verify the C Payment projection without duplicating proving or parameter storage.

The manifest v3 experimental profile uses four pairs: Bootstrap, Send, Receive and Control. Control admits Load, signed RefreshTimeAnchor and Unload at the proof layer. The fixture's two-wallet flow uses Bootstrap, Load, Send and Receive with controls disabled. Native signed-floor Refresh does not create the protected direct-exchange observation required for time-controlled Send; the SDK's Unload selection remains closed. [Native Control contracts](../../NATIVE_BACKEND.md)

Apple E5 uses the real App Attest service and key-binding assertion, with effect dispatches and returned originals retained through the actual EnrollmentOwner. Android uses the actual nonexportable hardware key and its original KeyMint attestation chain. This fixture issuer **does not independently verify FI attestation policy before signing E6**. Therefore these runs test native proof/key custody and recovery, not production FI admission, pinned-root/revocation qualification, or physical cross-device payment. The separate host chain covers two wallet identities. No successful full device run is claimed until its actual output is preserved.

Android instrumentation entry: `KagemushaSpartanRuntimeDeviceTest`. Package the actual `libkagemusha_spartan_device_fixture.so` as an androidTest JNI library and the three programs under androidTest assets `spartan-artifacts/`. Use the explicit disposable application namespace through the existing `kagemushaEnrollmentProbeApplicationId` test property. The dedicated nonexported Activity invokes Android strong biometric or device-credential authentication over the exact Native review before Send. It never accepts an app PIN or an injected success flag.
